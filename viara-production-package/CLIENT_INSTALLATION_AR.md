# تثبيت VIARA لدى العميل

## البداية السريعة

هذه الحزمة مخصصة لخادم Linux، أو Linux VM على Windows Server. على Windows افتح دليل البداية، ثم نفّذ التثبيت داخل Linux VM. لا يحتاج العميل Node.js أو الشيفرة المصدرية لبناء التطبيق.

1. جهّز Docker Engine وDocker Compose، وPython 3 وOpenSSL، وقرص البيانات والنسخ الاحتياطية. استخدم خادماً مخصصاً؛ السعة النهائية تُحدد بحسب عدد الأجهزة وحجم دراسات الأشعة وفترة الاحتفاظ.
2. تحقّق من SHA256 للحزمة المسلّمة، ثم استخرجها إلى مجلد مثل `/opt/viara`.
3. شغّل من داخل مجلد الحزمة:

```bash
bash setup.sh
```

4. أدخل رابط الموظفين HTTPS، ورابط بوابة المريض HTTPS، والترخيص الذي استلمته بشكل منفصل. اختيارياً أدخل عنوان IPv4 المحلي المخصص لاستقبال DICOM؛ القيمة الافتراضية تمنع استقبال الأجهزة من الشبكة حتى يجهزه مسؤول الشبكات.
5. ينتظر المشغّل جاهزية الخدمات ويوقف الإعداد برسالة واضحة عند الفشل. ترخيص غير صحيح يمنع الخادم من البدء. لا تعني جاهزية الخدمات اكتمال إعداد النطاق أو TLS أو الوصول عن بُعد.
6. عند وجود قاعدة جديدة خالية، يطلب المعالج بريد المدير واسمه وكلمة مرور مخفية من 16 حرفاً على الأقل. يُنشأ حساب Admin ويُطلب تغيير كلمة المرور عند أول دخول. لا توجد كلمة مرور افتراضية، ولا تتغير الحسابات الموجودة عند إعادة الإعداد.

## ماذا تضبط الحزمة تلقائياً؟

تولد مفاتيح وكلمات مرور مستقلة، وتحفظها داخل `.env` بصلاحيات مقيدة. تضبط أصول التطبيق والبوابة وWebAuthn باتساق، وتُبقي ملفات المريض والنسخ الاحتياطية والتخزين الطبي في وحدات بيانات دائمة. لا يطبع معالج الإعداد الترخيص أو الأسرار.

في حزمة Offline، يتحقق المشغّل من بصمات أرشيفات الصور، ويستوردها إلى Docker، ويشغّل معرفات صور ثابتة دون تنزيلها من سجل. يحتاج فحص ClamAV تحديث تعريفات الفيروسات إلى اتصال إنترنت أو آلية تحديث معتمدة من مسؤول الموقع؛ Offline للصور لا يعني تعطيل تحديثات الأمان. لا تتضمن الحزمة Docker Engine أو نظام تشغيل.

## إعادة التشغيل أو تغيير عنوان الموقع

لإعادة التشغيل بعد الإعداد:

```bash
bash setup.sh
```

تُحفظ الأسرار الحالية ولا تُولد من جديد. لتغيير إعدادات الموقع، يُجهّز مسؤول الموقع ملف JSON محمياً خارج مجلد التسليم:

```json
{
  "clinical_origin": "https://clinical.example.com",
  "portal_origin": "https://portal.example.com",
  "license_key": "VENDOR_ISSUED_KEY",
  "admin_email": "admin@example.com",
  "admin_name": "Site administrator",
  "admin_password": "UNIQUE_PRIVATE_PASSWORD_16_PLUS",
  "dicom_bind": "192.168.1.20"
}
```

```bash
chmod 600 /secure/site-settings.json
bash setup.sh --settings-file /secure/site-settings.json
```

لا تُرسل `.env` أو ملف إعداد الموقع للدعم عبر البريد. احتفظ بنسخة آمنة من مفاتيح التشفير ضمن خطة الاستعادة؛ فقدها يمنع فك بيانات المرضى. لا تستخدم معالج تثبيت جديد لتغيير أسرار قاعدة بيانات قائمة.

## إعداد الشبكات بواسطة مسؤول الموقع

يجب تجهيز DNS وHTTPS للبوابة العامة، وربطها بخدمة البوابة وحدها. تُتاح واجهة الموظفين وOHIF عبر الشبكة الداخلية أو VPN/ZTNA وmTLS حسب خطة الموقع. ملفات `remote-access`، إذا أُرفقت، قوالب تحتاج تعديل عنوان واجهة VPN والشهادات ومسارات الخوادم لدى العميل.

لا تنشر منافذ PostgreSQL أو Orthanc أو DICOM أو إدارة RIS مباشرة على الإنترنت. منافذ الويب في الحزمة مربوطة افتراضياً بـ loopback لتكون خلف مدخل HTTPS. اسم نطاق الموظفين يجب أن يبقى منفصلاً عن نطاق البوابة العامة.

بعد ضبط الشبكة، افتح رابط الموظفين لإكمال إنشاء حساب المدير بالطريقة المعتمدة، ثم اختبر دخول المريض والطبيب المحوّل، واستقبال دراسة DICOM، وكتابة تقرير نهائي، وتنزيله من البوابة. نفّذ استعادة نسخة احتياطية على بيئة معزولة قبل تشغيل بيانات المرضى.

## التشخيص والتحديث

```bash
docker compose ps
docker compose logs --tail 80 backend
```

راجع السجلات محلياً ولا تشارك بيانات المرضى أو الأسرار. عند التحديث احتفظ بـ`.env` ووحدات البيانات، وخذ نسخة احتياطية قابلة للاستعادة قبل تطبيق إصدار جديد. لا تستخدم `docker compose down -v` على بيانات العميل.

الترخيص وتكوين HTTPS وشهادات VPN وخطة النسخ الاحتياطية تُسلّم وتُعتمد لكل موقع بشكل منفصل. نجاح الإعداد التقني لا يغني عن قبول سير العمل السريري واختبار الحمل على شبكة العميل.
