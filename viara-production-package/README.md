# قالب تشغيل إصدار VIARA RCMS

> **الحالة: غير معتمد للتسليم كإصدار عميل.** يحتوي مجلد مساحة العمل على ملفات تطوير وإعدادات محلية. لا تسلّم ملف `.env` أو ملفات الترخيص أو كلمات المرور أو أرشيف ZIP قديم. يتطلب النشر إصدارًا معتمدًا وتفاصيل التهيئة الآمنة من VIARA.

## صور الإصدار

يستخدم `docker-compose.yml` صورًا مسبقة البناء ولا يبني الشيفرة المصدرية. يجب أن يوفّر مسؤول الإصدار مراجع صور معتمدة ومثبتة وسجلًا موثوقًا:

| متغير Compose | الصور |
|---|---|
| `VIARA_BACKEND_IMAGE` و`VIARA_FRONTEND_IMAGE` و`VIARA_PORTAL_IMAGE` و`VIARA_OHIF_IMAGE` | صور VIARA |
| `POSTGRES_IMAGE` | PostgreSQL |
| `CLAMAV_IMAGE` | ClamAV |
| `ORTHANC_IMAGE` | Orthanc |
| `REDIS_IMAGE` | Redis |
| `CADDY_IMAGE` | Caddy (optional public portal edge) |
| `WIREGUARD_IMAGE` | WireGuard (optional VPN profile) |

أدخل مراجع الصور كاملة كما وردت في سجل الإصدار، وفضّل مراجع digest مثل `registry.example/image@sha256:...`؛ لا تستخدم `latest` أو وسمًا متحركًا. يجب أن تتضمن صورة frontend عناوين البوابة وOHIF الخاصة بموقع العميل. اختبر جميع الصور والإعدادات في staging قبل اعتماد الإصدار.

## الإعداد والتشغيل

استخدم مضيف Linux مدعومًا، أو Linux VM على Windows Server. لا تستخدم ملف `.env` الموجود في مساحة العمل؛ أنشئ ملف إعداد محميًا من `.env.example`، وأدخل فقط القيم التي سُلّمت عبر قنوات الإصدار وإدارة الأسرار المعتمدة، واضبط عناوين HTTPS المصرح بها وبيانات WebAuthn. يجب أن تكون كلمة مرور PostgreSQL فريدة من 64 خانة hex حتى تبقى صالحة داخل عنوان الاتصال. قيم `PORTAL_PUBLIC_URL` و`VITE_OHIF_URL` مراجع لبناء صورة frontend لدى فريق الإصدار؛ تعديلهما وقت التشغيل لا يغيّر صورة منشورة. لتضمين OHIF، تُبنى صورة frontend بـ`VITE_OHIF_URL=/pacs-viewer/` ويُمرر reverse proxy هذا المسار إلى خدمة OHIF على مضيف تطبيق الموظفين نفسه. صورة OHIF يجب أن تتضمن ملفات VIARA المخصصة (`Dockerfile` و`entrypoint.sh` و`app-config.js` و`nginx.conf`) وأن تُنشر بهضم الإصدار المعتمد بعد بنائها؛ صورة OHIF upstream وحدها لا تحتوي هذه التعديلات. `CLIENT_URL` هو أصل التطبيق الدقيق دون مسار، ويستخدمه OHIF في CSP. لا تستخدم أصل OHIF مختلفًا لأن مصادقة الجلسة مرتبطة بنفس الأصل. العارض الداخلي بديل للمعاينة فقط وليس للقراءة التشخيصية أو القياس. اربط DICOM بعنوان واجهة الشبكة الطبية المقصودة عبر `PACS_DICOM_BIND` فقط، ثم قيّد الجدار الناري بعناوين أجهزة التصوير المعتمدة؛ القيمة الافتراضية loopback ولن تستقبل اتصالًا من الشبكة. سجّل الدخول إلى سجل الصور قبل التشغيل.

بعد استلام الإعدادات والصور المثبتة، شغّل خدمات Linux:

```sh
./scripts/start.sh
```

على Windows Server، شغّل `start.sh` داخل Linux VM المدعومة؛ لا تشغّل الحاويات كحاويات Windows أصلية. ملف `scripts/start.bat` مساعد لمشغّل Windows لديه Docker Compose موجّه إلى مضيف Linux متوافق، وليس بديلًا عن تجهيز الـVM أو ضبط مسارات bind mounts على المضيف. يجب أن يمر الوصول للمستخدمين عبر reverse proxy معتمد وHTTPS؛ منافذ التطبيقات المنشورة مربوطة بـloopback افتراضيًا.

## الوصول عن بُعد

- افصل المسارين: انشر بوابة المرضى والأطباء المحولين فقط عبر حافة عامة معتمدة وHTTPS، مثل Cloudflare Tunnel مع قواعد Nginx المرفقة في مستودع الإصدار. لا توجّه الإنترنت مباشرة إلى منافذ التطبيق أو قاعدة البيانات أو Orthanc أو DICOM.
- ملف Caddy داخل Compose اختياري (`caddy-ssl`) وينشر المنفذين 80 و443 على المضيف؛ لا تفعّله إلا بعد ضبط `DOMAIN` وDNS وTLS والجدار الناري ومراجعة سياسة المؤسسة. تشغيله ليس بديلاً تلقائياً عن Cloudflare Tunnel أو مراجعة الحافة.
- وصول الموظفين وOHIF يجب أن يكون عبر VPN أو شبكة Zero-Trust مع mTLS وشهادات عميل موثوقة. لا تستخدم بوابة المرضى كمدخل للموظفين أو لقراءة الصور التشخيصية.
- قالب حافة Nginx السريري لا يُنشأ تلقائياً من هذه الحزمة: يلزم ضبط عنوان واجهة VPN، واسم DNS، وشهادة الخادم وCA سريرية وإجراءات إصدار/إلغاء شهادات الأجهزة لدى العميل. تحقق من قواعد الجدار الناري قبل فتح الخدمة.
- قبل القبول السريري، اختبر تدفق صور DICOM كبيرة، الاستئناف/إعادة المحاولة، جلسات OHIF، زمن التقرير، أجهزة التصوير، واستعادة نسخة PACS على شبكة العميل. اختبار صحة الحاويات وحده لا يثبت هذه المسارات.

يتحقق `scripts/start.sh` و`scripts/start.bat` من إعداد Compose وثبات مراجع الصور قبل التشغيل. ينتظر سكربت Linux حتى تصبح خدمات PostgreSQL وClamAV وbackend وواجهات الويب وOHIF سليمة صحيًا، لكنه لا يتحقق من جاهزية Orthanc؛ افحص PACS/DICOM منفصلًا. يسحب Docker الصور المطلوبة عند بدء الخدمات. لا يطبع أي من السكربتين بيانات دخول أولية؛ استلمها عبر إجراء onboarding آمن.
تفعيل أو استبدال الترخيص يتم من **إعدادات النظام ← الترخيص والإصدار**؛ مجلد تحديث الترخيص القديم متوقف لأنه كان يكتب المفتاح إلى `.env` ثم يعيد تشغيل الحاوية بطريقة لا تطبق متغيرات البيئة المعدّلة.
تفرض سكربتات البدء أن تنتهي **كل** مراجع صور الخدمات بهضم `sha256` غير قابل للتغيير؛ أمر `docker compose up` اليدوي وحده لا يفرض هذا الشرط.

## بوابات التسليم

- أدوات التغليف في مستودع المصدر (`scripts/package-release.ps1` و`scripts/package-release.sh`) ترفض إنشاء الأرشيف ما لم تكن مراجع صور الخدمات العشر مثبتة بـ`sha256`؛ وضع Offline يتحقق من وجود كل صورة محلياً ويضيف بصمة لكل ملف تصدير. أدوات بناء الصور والتغليف لا تُضمّن في حزمة العميل. لا تضع الترخيص داخل القالب أو الحزمة، ولا تعتبر نجاح إنشاء ZIP اعتماداً للتشغيل السريري.
- طابق مراجع الصور وتواقيعها أو checksums، إن توفرت، مع إصدار اجتاز staging.
- تحقق من وجود كل migrations المسجلة في manifest ومطابقتها للمصدر، واختبر الترحيل على قاعدة staging فارغة.
- لا تشغّل `database/migrate.js --fresh` على قاعدة عميل؛ هذا الخيار يسقط مخطط `public` ويعيد إنشاءه.
- راجع الملفات المضمّنة؛ استبعد `.env` والمفاتيح الخاصة والرخص المحلية والسجلات والمخابئ وملفات التطوير.
- حافظ على volume `license_data` عبر التحديثات والنسخ والاستعادة؛ يحتوي الترخيص المفعّل وربط بصمة العتاد.
- راجع ربط المنافذ وTLS والجدار الناري والنسخ الاحتياطي والاستعادة وخطة الرجوع قبل الإنتاج.
- ينشئ `scripts/backup.sh` (وعلى Windows: `scripts/backup.bat`) نسخة PostgreSQL مشفرة بـ AES-256-GCM ومصحوبة تلقائيًا بأرشيف صور الأشعة DICOM المشفر (`.pacs.zip.enc`) الموثق ببصمات SHA-256، ويحفظهما في وحدة النسخ الاحتياطي المستمرة؛ احمِ مفتاح التشفير `BACKUP_ENCRYPTION_KEY` خارج الخادم.
- توفر الحزمة سكربتات الاستعادة المؤتمتة `scripts/restore.sh` و`scripts/restore.bat` التي تدعم الفحص الجاف لسلامة النسخة دون مساس بالبيانات (`--verify-only`)، أو الاستعادة الكاملة المعتمدة (`--confirm`) لقاعدة البيانات وصور الأشعة Orthanc بتسلسل ترانزاكشن آمن.
- راجع [دليل التعافي من الكوارث](../docs/DISASTER_RECOVERY_RUNBOOK_AR.md) و[دليل الاستعادة](../docs/runbooks/RESTORE.md) للاطلاع على خطوات التحقق اليدوي بعد الاستعادة ومطابقة سجل التدقيق الرقابي.
- سكربت `seed-demo` يمسح جداول العميل قبل إدخال بيانات تجريبية معروفة؛ لا تستخدمه إلا على قاعدة تقييم مؤقتة قابلة للتخلص منها وبعد تأكيد صريح.
- لا تنشئ أو تسلّم أرشيف إصدار قبل اجتياز قائمة التحقق والاختبارات على staging.

راجع [دليل تشغيل العميل](../docs/CLIENT_DEPLOYMENT_OPERATIONS_AR.md) و[قائمة تحقق النشر والتسليم](../docs/RCMS_DEPLOYMENT_CHECKLIST.md). الأدلة داخل مجلد `docs/` بهذه الحزمة مسودات مؤرشفة وليست تعليمات تشغيل معتمدة.
