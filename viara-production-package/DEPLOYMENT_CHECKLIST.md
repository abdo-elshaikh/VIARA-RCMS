# VIARA-RCMS — Deployment Checklist
## قائمة مراجعة النشر | v1.0.0-RC2

> **استخدام هذه القائمة:** نفِّذ كل بند بالترتيب قبل بدء أي نشر إنتاجي.  
> ضع علامة `[x]` على كل بند بعد إتمامه. لا تنتقل للمرحلة التالية قبل إغلاق جميع بنود المرحلة الحالية.

---

## المرحلة 1 — ما قبل النشر: متغيرات البيئة

### 1.1 عناوين URL والنطاقات

- [ ] **`CLIENT_URL`** — غيّر القيمة من `https://localhost:5173` إلى نطاق الواجهة الأمامية الحقيقي بـ HTTPS.  
  مثال: `CLIENT_URL=https://viara.yourhospital.com`

- [ ] **`ALLOWED_ORIGINS`** — غيّر القيمة من `https://localhost:5173,...` إلى النطاقات الإنتاجية الفعلية.  
  مثال: `ALLOWED_ORIGINS=https://viara.yourhospital.com,https://portal.yourhospital.com`

- [ ] **`PORTAL_CLIENT_URL`** — غيّر القيمة من `https://localhost:5174` إلى نطاق بوابة المرضى/الأطباء الحقيقي.  
  مثال: `PORTAL_CLIENT_URL=https://portal.yourhospital.com`

> ⚠️ **تحذير:** الخادم يرفض الإقلاع تلقائياً إذا كانت هذه القيم تحتوي على `localhost` في بيئة `NODE_ENV=production` (مُطبَّق في `validateEnv.js`). لن تحصل على رسالة خطأ مُضلِّلة — النشر سيفشل صراحةً.

---

### 1.2 مفاتيح التشفير والأسرار

- [ ] **`JWT_SECRET`** — تحقق من أنه قيمة عشوائية قوية (على الأقل 64 حرفاً من base64 أو hex).  
  للتوليد: `openssl rand -hex 64`  
  **يجب ألّا يكون** قيمة افتراضية أو placeholder.

- [ ] **`ENCRYPTION_KEY`** — تحقق من أنه مختلف عن `BLIND_INDEX_KEY` (يرفض الخادم التطابق صراحةً).  
  للتوليد: `openssl rand -hex 32`

- [ ] **`BLIND_INDEX_KEY`** — تحقق من أنه مختلف عن `ENCRYPTION_KEY`.  
  للتوليد: `openssl rand -hex 32`

- [ ] **`BACKUP_ENCRYPTION_KEY`** — تحقق من أنه منفصل عن `ENCRYPTION_KEY` (مطلوب للنسخ الاحتياطية المشفرة).

---

### 1.3 قاعدة البيانات

- [ ] **`DATABASE_URL`** / **`POSTGRES_*`** — تحقق من أن قيم المضيف وقاعدة البيانات والمستخدم وكلمة المرور تشير إلى قاعدة البيانات الإنتاجية الفعلية، وليس إلى localhost أو بيئة تطوير.  
  مثال: `DATABASE_URL=postgresql://viara_user:StrongPassword@db-host:5432/viara_production`

- [ ] **`POSTGRES_PASSWORD`** — تحقق من أنه قيمة قوية ومولَّدة عشوائياً.

---

### 1.4 خدمات خارجية

- [ ] **SMTP (البريد الإلكتروني):** تحقق من أن `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` تشير إلى خادم بريد إنتاجي فعلي.

- [ ] **ClamAV:** تحقق من أن `CLAMAV_HOST` يشير إلى خدمة ClamAV ضمن الشبكة الداخلية لـ Docker (القيمة الافتراضية `clamav` صحيحة في إعداد Compose).

- [ ] **Redis:** تحقق من أن `REDIS_URL` يشير إلى خدمة Redis ضمن الشبكة الداخلية (القيمة الافتراضية `redis://redis:6379` صحيحة في إعداد Compose)، وأن `REDIS_PASSWORD` مضبوط إذا كانت Redis محمية بكلمة مرور.

- [ ] **`RATE_LIMIT_STORE`** — يجب أن تكون القيمة `redis` في الإنتاج (يرفض الخادم `memory` صراحةً في `NODE_ENV=production`).

---

### 1.5 فحص نهائي لملف .env

- [ ] افتح ملف `.env` وابحث يدوياً عن أي قيمة تحتوي على `localhost` أو `127.0.0.1` أو `changeme` أو `example` أو `placeholder` وعالجها.
- [ ] تأكد من أن `NODE_ENV=production` مضبوط.
- [ ] تأكد من عدم تتبع ملف `.env` في Git: `git ls-files viara-production-package/.env` يجب ألّا يُعيد نتيجة.

## المرحلة 2 — ما قبل النشر: TLS والوكيل العكسي

> الخادم يعمل بـ HTTP داخل الشبكة الداخلية لـ Docker. **يجب** وجود وكيل عكسي (Nginx أو Traefik أو Caddy) على المضيف يُنهي TLS قبل إيصال الطلبات للحاوية.  
> راجع `docs/REVERSE_PROXY_TLS.md` للتعليمات التفصيلية.

- [ ] **شهادة TLS:** تحقق من صلاحية الشهادة وأنها لم تنتهِ.  
  للفحص: `openssl x509 -enddate -noout -in /path/to/cert.pem`  
  أو عبر المتصفح: تأكد من عدم ظهور تحذير "شهادة غير موثوقة" أو "منتهية الصلاحية".

- [ ] **ضبط HTTPS في الوكيل العكسي:** تحقق من أن Nginx/Traefik/Caddy مُضبوط للاستماع على المنفذ 443 بـ HTTPS وتمرير الطلبات داخلياً للحاوية.

- [ ] **إعادة توجيه HTTP → HTTPS:** تحقق من أن الوكيل يُعيد توجيه جميع طلبات HTTP (المنفذ 80) تلقائياً إلى HTTPS (المنفذ 443).  
  للاختبار: `curl -I http://<domain>` يجب أن يُعيد `301 Moved Permanently` مع `Location: https://...`

- [ ] **ترويسة HSTS:** تحقق من إضافة ترويسة `Strict-Transport-Security` في إعداد الوكيل.  
  مثال لـ Nginx: `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`  
  للتحقق: `curl -I https://<domain>` ثم ابحث عن `strict-transport-security` في الرد.

## المرحلة 3 — النشر: Docker Compose

> نفِّذ هذه الأوامر من داخل مجلد `viara-production-package/`.

```bash
cd viara-production-package
```

- [ ] **سحب أحدث الصور:**
  ```bash
  docker compose pull
  ```
  تأكد من اكتمال السحب دون أخطاء لجميع الخدمات.

- [ ] **تشغيل جميع الخدمات والانتظار حتى اكتمال فحوصات الصحة:**
  ```bash
  docker compose up -d --wait
  ```
  الخيار `--wait` يضمن عدم الانتقال للخطوة التالية إلا بعد نجاح جميع `healthcheck` المُضبوطة في Compose.

- [ ] **التحقق من حالة جميع الحاويات:**
  ```bash
  docker compose ps
  ```
  يجب أن تظهر جميع الخدمات بحالة `healthy` (وليس `starting` أو `unhealthy`).  
  الخدمات المتوقعة: `backend`, `frontend`, `portal`, `postgres`, `redis`, `clamav`, `orthanc`.

## المرحلة 4 — ما بعد النشر: التحقق من نقاط الصحة

- [ ] **فحص صحة الواجهة الخلفية (liveness):**
  ```bash
  curl -f https://<domain>/api/health/live
  ```
  المتوقع: رد `200 OK` مع جسم يحتوي `"status":"ok"` (أو ما يعادله).

- [ ] **فحص صحة الواجهة الخلفية (readiness — PostgreSQL + ClamAV):**
  ```bash
  curl -f https://<domain>/api/health/ready
  ```
  المتوقع: رد `200 OK` يُشير إلى جاهزية قاعدة البيانات وخدمة ClamAV. أي حالة غير 200 تعني وجود مشكلة في إحدى التبعيات.

- [ ] **تحميل الواجهة الأمامية في المتصفح:**  
  افتح `https://<domain>` في متصفح. يجب أن تظهر صفحة تسجيل الدخول بدون أخطاء في Console (F12).

- [ ] **تحميل بوابة المرضى/الأطباء في المتصفح:**  
  افتح `https://portal.<domain>` (أو النطاق المُضبوط في `PORTAL_CLIENT_URL`). يجب أن تظهر الصفحة الرئيسية للبوابة بدون أخطاء.

## المرحلة 5 — ما بعد النشر: قاعدة البيانات والخدمات

### 5.1 التحقق من اتصال قاعدة البيانات

- [ ] راجع سجلات الواجهة الخلفية للتأكد من نجاح الاتصال بقاعدة البيانات:
  ```bash
  docker compose logs backend | grep -i "database\|postgres\|pool\|connected"
  ```
  ابحث عن رسالة تُشير إلى نجاح الاتصال. غياب أخطاء `ECONNREFUSED` أو `password authentication failed` مؤشر إيجابي.

### 5.2 التحقق من اكتمال الهجرات

- [ ] تحقق من عدد الهجرات المُطبَّقة في سجلات الإقلاع:
  ```bash
  docker compose logs backend | grep -i "migrat"
  ```
  **العدد المتوقع: 194 هجرة.** أي عدد أقل يعني أن الهجرات لم تُطبَّق كاملاً — توقف فوراً وراجع أخطاء الهجرات قبل المتابعة.

### 5.3 التحقق من خدمة ClamAV

- [ ] تحقق من اتصال الخلفية بـ ClamAV:
  ```bash
  docker compose logs backend | grep -i "clam\|antivirus\|av"
  ```
  يجب ألّا تظهر أخطاء اتصال. خدمة ClamAV ضرورية لمسار رفع الملفات — أي فشل في الاتصال يعني أن رفع الملفات سيُرفض.

## المرحلة 6 — اختبارات الدخان (Smoke Tests)

> نفِّذ هذه الاختبارات يدوياً بعد النشر مباشرةً للتحقق من سلامة المسارات الرئيسية.

- [ ] **تسجيل الدخول:** سجّل الدخول بحساب موظف اختباري (Staff). تحقق من وصولك للوحة التحكم الرئيسية بدون خطأ.

- [ ] **إنشاء سجل مريض:** أنشئ سجل مريض تجريبي بالبيانات الأساسية (الاسم، تاريخ الميلاد، رقم الهوية). تحقق من حفظ السجل وظهوره في قائمة المرضى.

- [ ] **رفع دراسة DICOM:** ارفع ملف DICOM تجريبي للمريض المُنشأ. تحقق من اكتمال الرفع واستكمال فحص الفيروسات (ClamAV) بنجاح.

- [ ] **عرض الدراسة في OHIF Viewer:** افتح الدراسة المرفوعة في عارض DICOM (OHIF). تحقق من تحميل الصور وعرضها بشكل صحيح.

- [ ] **توليد تقرير:** أنشئ تقريراً طبياً تجريبياً مرتبطاً بالدراسة. تحقق من الحفظ والاسترجاع.

- [ ] **تسجيل الخروج:** سجّل الخروج وتحقق من:
  - إعادة توجيهك لصفحة تسجيل الدخول.
  - محاولة الوصول لأي صفحة محمية بعد الخروج تُعيد توجيهك لتسجيل الدخول (الجلسة مُلغاة فعلياً).

## المرحلة 7 — إجراء التراجع (Rollback Procedure)

> اتبع هذه الخطوات عند الحاجة للعودة للإصدار السابق.

### 7.1 إيقاف النشر الحالي

```bash
cd viara-production-package
docker compose down
```

### 7.2 تحديد الإصدار السابق والعودة إليه

- [ ] في ملف `.env`، عدِّل متغيرات الصور لتشير لوسم (tag) الإصدار السابق:
  ```env
  VIARA_BACKEND_IMAGE=viara-backend:v1.0.0-RC1   # مثال: الوسم السابق
  VIARA_FRONTEND_IMAGE=viara-frontend:v1.0.0-RC1
  ```
  (عدِّل الأسماء الفعلية وفق سجل الصور المستخدم في بيئتك.)

- [ ] اسحب الصور السابقة:
  ```bash
  docker compose pull
  ```

- [ ] أعد تشغيل الخدمات:
  ```bash
  docker compose up -d --wait
  ```

### 7.3 التراجع في قاعدة البيانات (إن لزم)

> ⚠️ **تحذير:** التراجع في هجرات قاعدة البيانات عملية خطيرة وغير قابلة للتراجع بسهولة. لا تنفِّذها إلا إذا أكد الفريق الفني أن الهجرات الجديدة تسببت في تلف البيانات.

- [ ] استعد أحدث نسخة احتياطية سابقة للإصدار الجديد:
  ```bash
  # اعثر على ملف النسخة الاحتياطية المناسب في مجلد النسخ الاحتياطية
  docker compose logs backup-service | grep "Backup completed"
  ```

- [ ] أوقف الخدمات التي تستخدم قاعدة البيانات:
  ```bash
  docker compose stop backend
  ```

- [ ] استعد النسخة الاحتياطية (راجع `docs/DISASTER_RECOVERY_RUNBOOK_AR.md` للتعليمات التفصيلية):
  ```bash
  # استخدم نقطة نهاية الاستعادة أو ادفع لعملية pg_restore مباشرة
  # التفاصيل في: docs/DISASTER_RECOVERY_RUNBOOK_AR.md
  ```

### 7.4 التحقق من نجاح التراجع

- [ ] تحقق من صحة الخدمات بعد التراجع:
  ```bash
  docker compose ps
  curl -f https://<domain>/api/health/ready
  ```
- [ ] نفِّذ اختبارات الدخان (المرحلة 6) للتأكد من عمل المسارات الرئيسية.

## ملاحظات أمنية مهمة

> هذه البنود لا تحتاج تنفيذاً في كل نشر، لكن يجب مراجعتها دورياً.

- **ملف `.env` سري:** لا تشاركه عبر البريد الإلكتروني أو أنظمة المراسلة غير المشفرة. استخدم مدير أسرار آمناً (مثل HashiCorp Vault, AWS Secrets Manager, أو Bitwarden).
- **تدوير المفاتيح:** راجع `docs/KEY_ROTATION_RUNBOOK_AR.md` للتعليمات الخاصة بتدوير مفاتيح التشفير دورياً.
- **النسخ الاحتياطية:** تتم تلقائياً يومياً (02:00 UTC). تحقق دورياً من وجودها وسلامتها.
- **تحديثات الأمان:** راجع نتائج `npm audit` في CI قبل كل نشر رئيسي.
