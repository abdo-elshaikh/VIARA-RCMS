# منظومة اختبارات الأداء والتحمل والاستعادة لمنصة VIARA
## VIARA Performance & Load Testing Harness

هذه المنظومة مخصصة لتنفيذ ومحاكاة كافة سيناريوهات وثيقة [PERFORMANCE_TEST_PLAN.md](../PERFORMANCE_TEST_PLAN.md) بدقة واحترافية متكاملة، وبدون الحاجة لتثبيت أي مكتبات خارجية ثقيلة (تعتمد على محرك Node.js الأصلي v20+).

## 🚀 كيفية التشغيل السريع (Quick Start)

تأكد من تشغيل خدمات المنظومة أولاً (`node start-services.js` أو تشغيل الخادم على المنفذ 3000 أو 5173).

### 1. تشغيل فحص استكشافي سريع (Smoke Test - 5 ثوانٍ، مستخدم واحد):
```bash
node performance-tests/run.js --quick
```

### 2. قياس خط الأساس لمستخدم واحد (PF-01 Single-User Baseline - 15 ثانية):
```bash
node performance-tests/run.js --users=1 --duration=15
```

### 3. تشغيل سيناريو محدد (مثال: الاستقبال وحجز المواعيد):
```bash
node performance-tests/run.js --scenario=02 --users=5 --duration=20
```

### 4. تشغيل سيناريو الدفع ومنع التكرار (Idempotency & Billing):
```bash
node performance-tests/run.js --scenario=04 --users=5 --duration=15
```

### 5. محاكاة الحمل اليومي المدمج (10 مستخدمين متزامنين لجميع الأدوار):
```bash
node performance-tests/run.js --scenario=08 --users=10 --duration=30
```

### 6. محاكاة الذروة التشغيلية (Peak Load - 25 أو 50 مستخدماً):
```bash
node performance-tests/run.js --scenario=08 --users=25 --duration=30
node performance-tests/run.js --scenario=08 --users=50 --duration=60
```

## 🎯 خيارات موجه الأوامر (CLI Options)

| الخيار | القيمة الافتراضية | الوصف |
|---|---|---|
| `--scenario=<ID>` | `all` | السيناريو المراد اختباره (`01` إلى `08` أو `all`) |
| `--users=<N>` | `1` | عدد المستخدمين الافتراضيين المتزامنين (Virtual Users - VUs) |
| `--duration=<N>` | `15` | مدة الاختبار بالثواني لكل سيناريو |
| `--target=<URL>` | `http://localhost:3000` | رابط الخادم المستهدف (أو `http://localhost:5173`) |
| `--quick` | `false` | تفعيل فحص سريع لجميع السيناريوهات (1 مستخدم، 5 ثوانٍ) |
| `--help` | - | عرض تعليمات وأمثلة الاستخدام |

## 📊 معايير القبول ومؤشرات الأداء (SLA Thresholds)

تم ضبط معايير القبول تلقائياً ومطابقتها مع الجدول الوارد في القسم 6 من `PERFORMANCE_TEST_PLAN.md`:

| المقياس | الحد الأقصى المقبول | المعنى التشغيلي |
|---|---|---|
| **معدل الأخطاء (Error Rate)** | `< 1.0%` | نسبة الطلبات غير المتوقعة (5xx / Timeouts) |
| **قراءة API العادية (p95)** | `≤ 500 ms` | سرعة استرجاع القوائم والبيانات |
| **قراءة API العادية (p99)** | `≤ 1500 ms` | سرعة أبطأ 1% من طلبات القراءة |
| **البحث والكتابة (p95)** | `≤ 1000 ms` | سرعة تسجيل المرضى، حفظ المسودات والحجز |
| **صور الأشعة (p95)** | `≤ 5000 ms` | سرعة استرجاع دراسات وبيانات PACS |

تظهر نتيجة التقييم الكلية `PASS` أو `FAIL` أو `INCOMPLETE`. تجاوز حد مقاس يجعل الأمر ينتهي برمز خروج `1`، وعدم توفر قياس مطلوب يجعله ينتهي برمز `2` بدلاً من نجاح مضلل. سيناريوهات الأداة الحالية لا تجمع بعد قياس زمن ظهور أول صورة؛ لذلك لن تكون جولة الأداء دليلاً كاملاً على قبول SLA الخاص بالصور حتى يضاف قياس من عميل العرض. فحص `--quick` استكشافي وليس اختبار قبول.

## 📝 مخرجات وتقارير الاختبار

عند انتهاء كل اختبار، تقوم المنظومة تلقائياً بما يلي:
1. **طباعة جدول تحليلي فوري في الـ Terminal** يوضح المتوسط، p50، p95، p99، الإنتاجية (req/s)، وتفصيل كل مسار API.
2. **إنشاء تقرير Markdown مفصل** داخل المجلد `performance-tests/reports/` يتضمن جداول قياسات دقيقة متوافقة مع متطلبات توثيق المشروع.
3. **تصدير كائن JSON كامل** للتشغيل لتمكين التحليل الآلي ومقارنة الجولات المتعاقبة في بيئات الـ CI/CD.
