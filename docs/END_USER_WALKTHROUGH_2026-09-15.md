# تقرير اختبار تجربة المستخدم النهائي — VIARA RIS/PACS
## End-User Experience Test Report
**التاريخ:** 15 سبتمبر 2026 · **المدة:** جلسة شاملة · **الأسلوب:** تقمّص مستخدم نهائي (مشرف/استقبال/كاشير/طبيب أشعة/مريض بوابة) عبر الواجهة التشغيلية الحية للنظام العامل فعلياً (backend + frontend + portal + DB حقيقية بـ 151 مريضاً)

---

## Executive Summary

اختبرتُ النظام كمستخدم حقيقي عبر **5 مراحل**: المشي الشامل لكل الصفحات (60+ نقطة نهاية)، رحلات الأدوار المختلفة، رحلات المستخدم الكاملة مع أخطاء متعمدة (12 سيناريو خطأ)، رحلة مريض البوابة كاملة، والاختبار المالي الحاسم (الدفع المزدوج المتزامن).

**الخلاصة العامة: النظام في حالة ممتازة تشغيلياً.** كل الصفحات تفتح، الأداء سريع (كل شيء < 700ms)، رسائل التحقق من الإدخال من أفضل ما رأيت (حقل-بحقل، واضحة، قابلة للتنفيذ)، حماية الدفعات المالية محكمة (مفتاح Idempotency إلزامي fail-closed)، وقفل الحساب تصاعدي التدرج مع تحذير قبل القفل.

**المشكلة الأخطر المكتشفة:** لا توجد حماية خلفية من تكرار تسجيل المرضى — التسجيل المتسلسل والمتزامن كلاهما يُنشئ سجلات مزدوجة (اختُبرت وأُعيد إنتاجها). الحماية الوحيدة في الواجهة الأمامية فقط.

**التقييم العام: 8/10** — نظام جاهز للاستخدام اليومي مع فجوات قليلة محددة.

## جميع المشاكل المكتشفة (تفصيلي)

### BUG-001 — لا حماية خلفية من تكرار المرضى
- **الصفحة/الوظيفة:** تسجيل مريض جديد (POST /patients)
- **النوع:** Bug / منع أخطاء · **الخطورة:** High · **التكرار:** دائم (كل تسجيل مكرر)
- **ما حاول المستخدم فعله:** تسجيل نفس المريض مرتين (نقرة مزدوجة أو إعادة إرسال)
- **الخطوات:** POST بنفس البيانات (firstName=Duplicate, lastName=CheckUser, phone=01234567891) مرتين متتاليتين، ثم مرتين **متوازيتين** بPromise.all
- **ما حدث:** 201 + 201 في الحالتين — **سجلّان طبيان منفصلان لنفس الشخص**
- **المتوقع:** الطلب الثاني يُرفض بـ 409 مع اقتراح المريض الموجود
- **لماذا مشكلة:** في الرعاية الصحية = تاريخ طبي مجزأ، حساسيات مفقودة، وفواتير مزدوجة. حارس الواجهة (المطابق التلقائي) لا يعمل عند النقر المزدوج السريع أو أي عميل API
- **الحل:** فهرس فريد جزئي على `(phone_hash)` حيث الحالة نشطة + اعتراض 23505 → 409 مع بيانات المريض الموجود؛ أو فحص pre-insert بقفل `FOR UPDATE` على phone_hash. (الواجهة تعرض بالفعل لوحة "المريض موجود؟ اختر" — اربط الـ 409 بها)

### UX-002 — رسائل قواعد العمل بالعربية فقط
- **الصفحة:** الكاشير — تحصيل دفعة على فاتورة فحص بصبغة
- **النوع:** Consistency/UX · **الخطورة:** Medium
- **ما حدث:** حاولت الدفع على INV-20260910-000004 فرفض النظام بحقٍّ مشروع لكن بالرسالة: *"هذا الفحص يتطلب صبغة وريدية. يجب تسجيل وإضافة صبغة ومستلزمات الفحص إلى الفاتورة أولاً"* — **بالعربية فقط**
- **المشكلة:** كاشير يعمل بواجهة إنجليزية يفاجأ برسالة عربية. (نمط موثق في المراجعة السابقة §F9.1 وما زال قائماً في المسارات المالية)
- **الحل:** آلية `label(en, ar)` الموجودة أصلاً في invoiceController تُعمَّم على كل رسائل قواعد العمل، مع تمرير لغة الجلسة

### UX-003 — نص خطأ قاعدة البيانات التقني يصل للمستخدم
- **الصفحة:** تفاصيل مريض بمعرّف غير صالح (GET /patients/not-a-uuid)
- **النوع:** Error Handling · **الخطورة:** Medium
- **ما حدث:** 400 برسالة `"Invalid value: invalid input syntax for type uuid: \"not-a-uuid\""` — نص Postgres الخام
- **المتوقع:** 404 ودود "المريض غير موجود / Patient not found"
- **الحل:** errorHandler يعترض `22P02` على مسارات UUID → 404 موحدة (التعيين موجود جزئياً في errorHandler — أكمله لمسارات المريض)

### UX-004 — حقل الجنس حساس لحالة الأحرف
- **الصفحة:** تسجيل مريض · **النوع:** Validation/منع أخطاء · **الخطورة:** Medium
- **ما حدث:** `gender: 'female'` (صغيرة) → رفض 400 "Gender must be Male, Female, or Other" — الرسالة توضح القيم الصحيحة (جيد) لكن الرفض ذاته كان يمكن تجنبه
- **الحل:** `.transform(v => v?.charAt(0).toUpperCase() + v?.slice(1).toLowerCase())` في المخطط — اقبل أي حالة وطبّع

### PERF-005 — نقطة الطابور الأثقل (464–650ms)
- **الصفحة:** الاستقبال/قائمة العمل/الممرضة (polling كل 15 ثانية) · **النوع:** Performance
- **قِيَمي:** 464–650ms عبر جلسات مختلفة (أثقل نقطة في النظام كله). كاش KPI (10s) خفّف الضربات المتكررة لكن الضربة الأولى بعد كل تحول تبقى بطيئة
- **الحل:** (موثق في مراجعة الأداء) — `COUNT(*) OVER()` بدل الاستعلام المزدوج + الفهارس الثمانية المضافة في الترحيل 163 (تحقق من تطبيقه على البيئة)

### UX-006 — خطأ "الصبغة المطلوبة" بلا مخرج إجرائي
- **الصفحة:** الكاشير — تحصيل دفعة · **النوع:** Workflow/UX · **الخطورة:** Medium
- **ما حدث:** الرسالة تخبر *ما* ينقص (الصبغة والمستلزمات) لكن لا تخبر *أين/كيف* — الكاشير الجديد سيحاول البحث
- **الحل:** أضف للرسالة إجراء: زر "فتح بنود الفاتورة" (deep-link لتبويب البنود في نفس الشاشة). في الـ API: أرجع `action: 'add_consumables', invoiceId` لتلتقطه الواجهة

### SEC-007 — التوكن يبقى صالحاً بعد الخروج
- **ما حدث:** بعد POST /logout (200)، توكن الوصول يعمل (GET /profile = 200) حتى انتهائه (~1h)
- **التقييم:** النمط قياسي (refresh token يُبطل فعلياً في القاعدة بـ revoked_reason='logout' ✓، والوصول قصير العمر) — لكن لنظام طبي، قائمة denylist فورية أو تقصير العمر لـ 15 دقيقة مع تجديد شفاف يرفع الامتثال
- **الحل:** session check موجود بالفعل (authMiddleware يفحص جلسة!) — تأكد أن الخروج يُبطل السجل المرتبط فيتحول 200 إلى 401 فوراً

### UX-008 — الشات بلا سقف طول رسالة مُعلن
- **ما حدث:** رسالة 3000 حرف → 201 مقبولة
- **الحل:** سقف 2000 حرف في المخطط + عدّاد حروف في صندوق الإرسال

### CONS-009 — تعريفات نقاط نهاية مكررة
- `getMachines` و`getModalities` كلاهما → `/machines`؛ `getNotificationUnreadCount` يستقبل `limit` يتجاهله الخادم. تنظيف داخلي (لا أثر للمستخدم) — يقلل الالتباس عند الصيانة

### PERF-010 — قائمة أنواع الفحوص 661ms
- الخطوة الأولى في معالج الحجز — يجب أن تكون فورية (lookup صغير). سبب محتمل: استعلام التسعير/الفروع مدمج. اقتراح: فهرس أو كاش قصير

## ما نجح بامتياز (أُثبت بالاختبار الحي)

| المجال | الدليل الحي |

| **رسائل التحقق** | حقول فارغة/بريد خاطئ/اسم 300 حرف/تاريخ معكوس/هاتف بحروف → كل واحدة برسالة حقل-بحقل دقيقة ("Phone must be 10-15 digits") |
| **تغيير كلمة المرور** | ضعيفة → "at least 8 characters" · حالمة خاطئة → "Current password is incorrect" · نفس القديمة → "must be different" — ثلاث رسائل مميزة |
| **الحماية المالية** | الدفع بلا Idempotency-Key → 400 (fail-closed) · سالب → مرفوض · قاعدة الصبغة تُفرض · فتح وردية مزدوج → 409 "You already have an open cashier shift" |
| **قفل الحساب** | المحاولة 4: *"Warning: 1 attempt remaining"* · المحاولة 5: قفل 15 دقيقة برسالة واضحة — تدرج مثالي |
| **البوابة (المريض)** | دخول بـ MRN/كلمة مرور · أخطاء موحدة "Invalid credentials" (لا كشف وجود حساب) · طلب موعد 201 · تاريخ خاطئ → 400 واضح · السجلات/الفواتير/الرسائل/الإشعارات كلها 200 |
| **فصل الأدوار** | الكاشير ممنوع من السريريات (403) والطبيب من الماليات (403) — **والواجهة تستخدم نقاط النهاية المُبوّبة** (جرس الطبيب يستعمل my-notifications = 200 وليس مسار الإدارة الممنوع) |
| **بوابة الإعدادات** | تبويبات AI/قاعدة البيانات للمطور فقط — مخفية عن المشرف في الواجهة (canAccessSettingsSection) فلا ترى الـ 403ات |
| **الأداء العام** | 60+ نقطة نهاية: كلها < 700ms · دخول→لوحة تحكم = 708ms إجمالاً · صفر نقاط بطيئة (>1.5s) |
| **الصفحات العامة** | landing/الصفحة العامة/لوحة العرض تعمل دون مصادقة |

## التحسينات السريعة Quick Wins (أثر كبير/جهد صغير)
1. **حارس التكرار الخلفي** (BUG-001): فهرس فريد جزئي + 409 — نصف يوم عمل
2. **تطبيع حالة الجنس** (UX-004): سطر transform واحد
3. **اعتراض 22P02** (UX-003): فرع واحد في errorHandler
4. **سقف الشات** (UX-008): سطر max في المخطط + عدّاد
5. **إجراء مقترح في خطأ الصبغة** (UX-006): حقل action في الاستجابة + زر في الواجهة

## التحسينات طويلة المدى
1. **ثنائية لغة رسائل قواعد العمل** (UX-002): تعميم آلية label(en,ar) على كل المسارات — مشروع تدريجي
2. **بطاقة الطابور**: `COUNT(*) OVER()` (PERF-005) + التحقق من تطبيق فهارس الترحيل 163
3. **إبطال فوري للجلسة عند الخروج** (SEC-007)
4. **كاش قائمة أنواع الفحوص** (PERF-010)

## اقتراح Workflow محسّن — تحصيل فاتورة فحص بصبغة
**الحالي:** الكاشير يحاول الدفع → يُرفض برسالة الصبغة → يبحث بنفسه عن مكان إضافة المستلزمات → يعود للدفع.
**المقترح:** عند فتح فاتورة فحص يتطلب صبغة *قبل أي محاولة دفع*، يعرض النظام لافتة صفراء "هذا الفحص يتطلب صبغة وريدية — أضف البنود (زر)" مع الأصناف المقترحة مسبئياً من كتالوج المستلزمات المرتبط بنوع الفحص. يحوّل الرفض المتأخر إلى توجيه استباقي.
