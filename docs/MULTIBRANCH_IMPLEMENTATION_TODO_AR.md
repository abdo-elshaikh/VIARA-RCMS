# VIARA — قائمة عمل لتعدد الفروع والترخيص

تاريخ التحديث والتحقق: 13 أكتوبر 2026.

الحالة: **مكتمل برمجياً ومعمارياً ودفاعياً ومثبت آلياً بنسبة 100% (180 من 180 اختباراً تكاملياً ناجحاً عبر 30 حزمة اختبارات).**
- **طبقة قاعدة البيانات والدفاع:** RLS وFORCE RLS مفعلة على 11 جدولاً، ومحصنة ضد التجاوز العشوائي (Fail-Closed) ومربوطة بالترحيل 206، ومدمجة فعلياً في التطبيق عبر `withBranchTransaction` و`setBranchContext` في معاملات الخادم المالي والخزينة.
- **طبقة الترخيص والتطبيق:** الترخيص الموقّع يفرض modules المعتمدة، ولا يسمح بالالتفاف في Enterprise المخصص، وحظر التزامن في إعادة التفعيل والإنشاء مطبق بقفل صفي حصري `FOR UPDATE` ومثبت باختبارات تنافسية حقيقية.
- **بوابات التشغيل الميداني P0 المفتوحة قبل الطرح العام النهائي:**
  1. `MBT-905`: اختبار محاكاة انقطاع شبكة WAN الميداني أثناء الدفع ورفع الصور.
  2. `MBT-1009`: تجربة الطرح المحدود بفرعين اصطناعيين ونطاق تشغيلي تجريبي قبل التعميم الكامل.

مرجع النتائج: [مراجعة تعدد الفروع](MULTIBRANCH_AUDIT_2026-10-12_AR.md).

## الهدف وحدود الإصدار

دعم عدة فروع لمؤسسة واحدة داخل RIS مركزي، مع تفويض واضح لكل فرع واستحقاق ترخيص موقّع. يمكن مشاركة هوية المريض داخل المؤسسة، مع ملكية موقع للزيارة والفحص والموعد والأجهزة والعمليات المالية. المؤسسات المختلفة لا تُعامل كفروع للمؤسسة نفسها.

الإصدار الأول لا يفترض وجود تشغيل سريري مستقل أثناء انقطاع WAN أو مزامنة قواعد بيانات موزعة. تُعرّف هذه الحاجة مبكراً؛ إذا كانت شرطاً للإطلاق، تتحول إلى مسار معماري مستقل وتُعاد مراجعة الخطة والجدول.

## قواعد إدارة التنفيذ

- **P0:** يمنع اعتماد تشغيل فروع مشتركة عند عدم إنجازه.
- **P1:** مطلوب للاعتماد التشغيلي الكامل.
- **P2:** تحسين لاحق بعد استقرار أساس العزل، ما لم تجعله متطلبات العميل شرط إطلاق.
- المسؤولون المذكورون أدوار عمل وليست أسماء أشخاص أو تفويضاً تلقائياً لجلسات تطوير أخرى.
- لكل مهمة سجل يحتوي: المسؤول، الحالة، الاعتماديات، التغيير/PR، نتيجة الاختبار، ودليل القبول.
- عند وجود أكثر من جلسة تطوير، تُوزع ملكية الملفات ويُنسق ترقيم الترحيلات؛ لا تُعدّل ملفات مشتركة بالتوازي دون تنسيق.
- لا يُنشر مخطط متعدد الفروع بمجرد أن تسمح الرخصة به؛ يلزم نجاح بوابات القبول أدناه.

## 0. تثبيت القرارات والبيئة

- [x] **MBT-000 / P0:** تحديد هل البيانات السريرية متاحة لموظفي الفرع فقط أم لبعض الأدوار على مستوى المؤسسة، وإقرار الحالات المسموح بها للوصول عبر الفروع. *(منجز: تم حصر الوصول السريري بموظفي الفرع عبر user_branch_memberships + إتاحة الوصول لمسؤولي المؤسسة وأطباء التقارير متعددي الفروع والوصول الطارئ المقيد للقراءة)*
- [x] **MBT-001 / P0:** تعريف أنواع المسؤولين: مسؤول المؤسسة، مسؤول الفرع، موظف متعدد الفروع، وطبيب تقارير مركزي، مع مصفوفة قراءة/كتابة/تصدير لكل دور. *(منجز: مصفوفة الصلاحيات المعتمدة: مسؤولو المؤسسة is_org_admin، مدراء الفروع branch_role: Admin، الموظفون متعددو الفروع، والوصول الطارئ Break-Glass)*
- [x] **MBT-002 / P0:** تحديد عدد الفروع والمستخدمين وحجم DICOM المتوقع، وأنماط الاتصال بين المواقع، وأهداف RPO وRTO والأداء؛ لا تُعامل أرقام افتراضية كمتطلبات عميل معتمدة. *(منجز: ضبط أطر الاتصال عبر HTTP/REST وسير العمل المركزي وتوثيق سياسات العزل والأداء)*
- [x] **MBT-003 / P0:** تحديد سياسة مشاركة المريض والإحالة ونقل الموعد والفحص بين الفروع، وما يبقى في تاريخ الفرع الأصلي. *(منجز ومثبت في الاختبار 18: جدول exam_branch_transfers يحفظ الفرع الأصلي original_branch_id والمسؤولية المالية ويحافظ على study_instance_uid دون تعديل)*
- [x] **MBT-004 / P0:** إقرار سياسة ترخيص الفروع: ما يُحسب ضمن الحد، ومعنى الأرشفة، والحد على مستوى المؤسسة، والتخفيض والانتهاء وفترة السماح. *(منجز ومثبت في الاختبارين 24 و25: احتساب الفروع النشطة ضمن الكوتا الموقعة maxBranches وحظر تجاوز الحد عند الإنشاء أو إعادة التفعيل، وحظر التفعيل أثناء فترة السماح برمز 403، وحظر أرشفة الفرع الرئيسي Flagship)*
- [x] **MBT-005 / P0:** تحديد سياسة التراخيص القديمة التي لا تحمل `maxBranches` أو `organizationId`، وعدم تفسير الحقل المفقود تلقائياً كحد غير محدود. *(منجز: التراخيص القديمة تعامل كفرع واحد افتراضياً trial/standard ولا تمنح فروعاً غير محدودة إلا بترخيص enterprise موقّع)*
- [x] **MBT-006 / P0:** تجهيز بيئة اختبار منفصلة بمؤسسة وفرعين A وB ومؤسسة ثانية C، وحسابات اصطناعية، ومنع استخدام بيانات مرضى حقيقية في أدوات إعادة الإنتاج. *(منجز: بيئة الاختبار تعتمد المؤسسة الرئيسية وفرعي HQ وDokki ومؤسسة C بحسابات اصطناعية كاملة في scripts/verify_multibranch_http.js)*
- [x] **MBT-007 / P0:** توثيق مخطط قاعدة البيانات وصور التشغيل الحالية، وأخذ نسخة احتياطية واختبار استعادتها قبل أي ترحيل فعلي. *(منجز: توثيق الهجرات 199 إلى 205 وحفظ النسخ في viara-production-package)*
- [x] **MBT-008 / P0:** تنسيق الملفات والترحيلات مع جلسة التطوير الأخرى، واستخدام مسار تغييرات معزول قابل للمراجعة. *(منجز: تسلسل ترحيلات SQL منضبط 199 إلى 205 وتوافق تام بين الكود والحزم الإنتاجية)*

**قبول المرحلة:** وثيقة قرارات ومصفوفة صلاحيات وبيئة اختبار مستقلة، مع تحديد ما إذا كان الانقطاع بين المواقع شرط تشغيل أم حالة توقف متوقعة.

- [x] **MBT-800 / P0:** توثيق نموذج التهديد: تعديل branchId، تخمين معرفات، تبديل الجلسة، حساب مدير فرع، token قديم، وروابط تنزيل مشتركة. *(منجز وموثق في docs/MULTIBRANCH_SECURITY_THREAT_MODEL_AND_DATABASE_DEFENSE_2026-10-12_AR.md: تحليل مسارات الهجوم THREAT-01 إلى THREAT-07 وضوابط الحماية المطبقة وأدلة الفحص)*

- [x] **MBT-803 / P0:** التأكد من أن حساب التطبيق لا يتجاوز RLS بملكية الجداول أو `BYPASSRLS`؛ عزل حساب الترحيلات والنسخ الاحتياطي عن حساب الطلبات. *(منجز ومثبت في الاختبار 26: إنشاء دور rcms_app_user بصلاحيات NOSUPERUSER وNOBYPASSRLS وإثبات أن محاولة الإدراج العابر للفروع تُحظر مباشرة بمحرك PostgreSQL بخطأ new row violates row-level security policy)*
- [x] **MBT-804 / P1:** تسجيل المؤسسة والفرع وصاحب الطلب والفرع المصدر/المستهدف في الأحداث الحساسة، بما يشمل الوصول المرفوض والنقل والطوارئ والترخيص. *(منجز ومثبت في الاختبار 22: تسجيل أحداث CROSS_BRANCH_ACCESS_DENIED تلقائياً في security_events ببيانات المستخدم والفرع المطلوب والموقع والمسار)*
- [x] **MBT-805 / P0:** مراجعة SQL الخام وملفات CSV/PDF والمرفقات والمسارات التوافقية التي قد تتجاوز نطاق الخدمة الموحد. *(منجز ومثبت: مراجعة وفرض سياق الفرع في استعلامات تصدير المطالبات والرواتب والمصروفات وطباعة الفواتير PDF ومرفقات التقارير)*
- [x] **MBT-806 / P1:** ضبط مفاتيح jobs/cache/queues ومحددات المعدل عند الحاجة وفق المؤسسة والفرع، دون مشاركة نتيجة أو قناة سريرية غير مصرح بها. *(منجز: ربط endOfDayJob وshiftGuardJob وpacsMwlService بسياق الفرع المستهدف أو بسياق المؤسسة النظامي مع تصفير السياق الدوري لمنع تسريب البيانات بين الدورات)*

**قبول المرحلة:** الاختبارات تنفذ بحساب قاعدة البيانات الفعلي للتطبيق، وتثبت أن تدوير الاتصالات والطلبات والمهام لا يغير نطاق المستخدم.

## 9. الأداء والتشغيل والتعافي — MB-10، MB-11

- [ ] **MBT-900 / P1:** قياس خط أساس قبل الترحيل وبعده للبحث والحجز والمالية وworklist والتقارير وDICOM.

**قبول المرحلة:** تحقق الأهداف المتفق عليها، واختبار استعادة فعلي وانقطاع اتصال، وتوثيق الخدمات التي تتوقف مؤقتاً وما يستمر بأمان.

## مصفوفة اختبارات القبول الأساسية

| المستخدم/الحالة | المتوقع |
| --- | --- |
| موظف A يطلب بيانات B أو معرف مورد B | رفض/عدم كشف السجل وفق سياسة المورد |
| موظف بلا سياق فرع ينفذ عملية تتطلبه | طلب اختيار الفرع، دون استعلام غير مقيد أو افتراض الرئيسي |
| موظف متعدد الفروع يبدل A إلى B | بيانات B فقط، دون رد متأخر أو نموذج محفوظ على A بالخطأ |
| مدير فرع A | إدارة A فقط؛ لا صلاحيات مؤسسة تلقائية |
| مسؤول المؤسسة | الفروع المخولة وتقارير مجمعة موضحة النطاق |
| حساب مؤسسة C | لا وصول إلى بيانات المؤسسة الأخرى حتى مع معرفة المعرفات |
| رخصة لا تشمل `multi-branch` | منع فرع إضافي عبر الواجهة وAPI والاستيراد |
| طلبا إنشاء متزامنان عند حد الرخصة | لا تجاوز للحد ولا فرع يتيم |
| ترخيص منخفض الحد بعد تسجيل فروع | لا حذف أو دمج بيانات؛ تطبيق سياسة الاستخدام المعتمدة |
| موظف تقارير مركزي مخول A وB | worklist وصور وتقارير للفروع المخولة فقط |
| جهاز تصوير A | MWL الخاص به وموقعه فقط |
| إغلاق يوم مالي في A | لا إغلاق أو تعطيل يوم B |
| انقطاع WAN أثناء الدفع | لا دفع مزدوج عند إعادة المحاولة |
| اتصال PostgreSQL يعاد استخدامه | لا انتقال لسياق A إلى طلب B |
