# دليل إعداد وتشغيل VIARA للعميل

**الغرض:** مرجع عملي لتجهيز VIARA، تفعيل الترخيص، تشغيله في شبكة داخلية أو استضافة، حماية الخدمة والبيانات، ثم تحديث الإصدار بأمان.  
**الجمهور:** مسؤول تقنية المعلومات، مسؤول قواعد البيانات، مسؤول الشبكة، ومسؤول النظام لدى العميل.  
**النطاق:** دليل تشغيلي يجب مواءمته مع الإصدار والحزمة المرخصة التي تسلّمها VIARA للعميل.

> **تنبيه قبل البدء:** هذا المستودع يحتوي الشيفرة وملفات تطوير/نشر مرجعية، وليس بديلًا عن حزمة إصدار موثقة ومفتاح ترخيص وبيانات دخول تسلّمها VIARA عبر قناة آمنة. لا تشغّل إعدادات `.env.example` كما هي في الإنتاج؛ فهي قوالب وليست أسرارًا أو إعدادًا صالحًا للنشر العام. لا تستخدم حسابات أو كلمات مرور تجريبية مع بيانات حقيقية. تحقق من متطلبات الترخيص والامتثال وسياسة الاحتفاظ بالبيانات لدى مؤسستك قبل إدخال بيانات مرضى.

## 1. ملخص قرار الاستضافة

| بيئة العميل | المسار الموصى به | ملاحظات |
|---|---|---|
| مركز أشعة أو مستشفى على شبكة داخلية | خادم Linux فعلي أو آلة افتراضية Linux مع Docker Compose | مناسب لـ PostgreSQL وOrthanc والتخزين المستمر. اربط DICOM بشبكة الأجهزة المصرح بها فقط. |
| Windows Server في الموقع | آلة افتراضية Ubuntu/Debian على Hyper-V أو VMware/Proxmox، ثم Docker Compose داخل الآلة | خدمات VIARA الحالية تعتمد حاويات Linux. لا تشغّلها كحاويات Windows أصلية، ولا تعتمد Docker Desktop كخادم إنتاج على Windows Server. يمكن للمستخدمين وأجهزة الإدارة استخدام Windows عبر المتصفح. |
| جهاز Windows/Linux للتقييم | Docker Desktop أو Docker Engine وحزمة التقييم التي سلّمها المورد | للتجربة فقط؛ لا تضع بيانات مرضى فعلية على جهاز مشترك أو غير محمي. |
| استضافة سحابية على VM | VM Linux خاصة، أقراص ثابتة، جدار ناري، TLS، ونسخ احتياطية خارجية | يعامل PACS وDICOM كخدمات ذات بيانات دائمة وحساسة؛ اختر منطقة تخزين متوافقة مع سياسة العميل. |
| Kubernetes أو خدمات PaaS/قاعدة بيانات مُدارة | تصميم ونشر مخصصان واعتماد مسبق من فريق التشغيل | أمثلة Kubernetes والسحابة في README مرجعية وليست حزمة Helm أو إعدادًا جاهزًا. كثير من PaaS لا توفر تخزينًا دائمًا ملائمًا لأرشيف DICOM. لا تنقل Orthanc أو PostgreSQL إلى خدمة مُدارة دون تصميم واختبار التكامل والاستعادة. |

**التوصية الافتراضية للإنتاج:** Linux LTS + Docker Compose + reverse proxy داخلي/خارجي + شهادة TLS + تخزين دائم ونسخ احتياطية مجرّبة. عند وجود Windows Server، استضف Linux VM عليه بدل محاولة تشغيل المكونات كتطبيق Windows أصلي.

## 2. التخطيط والموارد والشبكة

### 2.1 متطلبات تخطيط أولية

المتطلبات التالية نقطة بدء للتقييم، وليست ضمان سعة أو بديلًا عن تقدير حجم الصور وعدد المستخدمين:

| الاستخدام | CPU | RAM | قرص النظام/التطبيق |
|---|---:|---:|---:|
| تقييم محدود أو موقع صغير | 4 أنوية | 8 GB كحد تخطيطي أولي | SSD بسعة 50 GB أو أكثر |
| تشغيل إنتاجي ابتدائي | 8 أنوية أو أكثر | 16–32 GB أو أكثر حسب الأحمال | NVMe/SSD؛ افصل مساحة قاعدة البيانات وPACS والنسخ الاحتياطية قدر الإمكان |

احسب سعة PACS من متوسط حجم الدراسة وعدد الدراسات وفترة الاحتفاظ والنمو المتوقع، ثم أضف مساحة للنسخ الاحتياطية ولقطات التخزين. لا تعتبر سعة قرص نظام التشغيل تقديرًا كافيًا لأرشيف الصور. راقب IOPS، امتلاء القرص، الذاكرة، ووقت الاستجابة في بيئة العميل قبل اعتماد السعة.

### 2.2 المنافذ ومسارات الشبكة

الحاويات المنشورة في Compose تتضمن الواجهة، بوابة المرضى/الأطباء، API، PostgreSQL، ClamAV، Orthanc، وOHIF. راجع ملف Compose الخاص **بالحزمة المسلّمة** قبل فتح المنافذ؛ قد تختلف القيم باختلاف الإصدار والإعداد.

| الخدمة | الاستخدام | قاعدة التعرض |
|---|---|---|
| HTTPS 443 (وHTTP 80 للتحويل فقط عند الحاجة) | واجهة الموظفين والبوابة وAPI عبر reverse proxy | المسموح للمستخدمين المستهدفين فقط؛ لا تعرض HTTP غير المشفر لتسجيل الدخول أو بيانات مرضى. |
| DICOM TCP 4242 افتراضيًا | C-STORE / DICOM من أجهزة التصوير إلى Orthanc | افتحه فقط من عناوين/شبكات الأجهزة الطبية أو VPN، واضبط `PACS_DICOM_BIND` على عنوان واجهة الشبكة المطلوبة لا `0.0.0.0` دون مبرر. |
| PostgreSQL 5432 | اتصال داخلي للتطبيق والإدارة | غير متاح من الإنترنت أو أجهزة المستخدمين؛ الربط المحلي الافتراضي هو الخيار الآمن ما لم توجد بنية DB معزولة مصممة لذلك. |
| Orthanc REST 8042 | واجهة إدارة داخلية لـ Orthanc | محلية/شبكة إدارة موثوقة فقط؛ لا تنشرها مباشرة إلى الإنترنت. |
| OHIF 3005، backend 3000، frontend 5173، portal 5174 | اتصالات داخلية أو خلف reverse proxy بحسب الحزمة | أبقها مربوطة إلى loopback أو شبكة الحاويات ما أمكن، ومرّر الدخول العام عبر TLS proxy فقط. |

لا تفتح كل المنافذ لمجرد أن الحاويات تستخدمها. حدّد مصادر الوصول لكل منفذ، ونسّق منافذ DICOM وAE Title وIP مع مهندس أجهزة التصوير قبل الاختبار. لا تستخدم إعدادات المنافذ الافتراضية كسياسة جدار ناري عامة.

## 3. التحضير والتفعيل

### 3.1 معلومات يجهزها العميل قبل التثبيت

1. اسم الجهة/الفرع ومسؤول استلام وتشغيل النظام.
2. طراز الخادم أو مواصفات الآلة الافتراضية، ومساحة التخزين المخصصة لـ PostgreSQL وPACS والنسخ.
3. أسماء DNS أو عناوين IP، وما إذا كان النشر داخليًا فقط أو متاحًا من الإنترنت.
4. النطاقات التي ستُستخدم لواجهة الموظفين والبوابة، مثل `ris.example.org` و`portal.example.org`.
5. شهادة TLS المناسبة. للشبكات المغلقة استخدم PKI المؤسسة وثبّت شهادة الجذر على أجهزة العملاء.
6. الشبكات/العناوين الثابتة لأجهزة التصوير، AE Title، منفذ DICOM، ومتطلبات VLAN/VPN.
7. خادم SMTP ومزود الرسائل إن كان العميل يريد تفعيل الإشعارات، بعد اعتماد سياسات الخصوصية والعقود.
8. سياسة RPO/RTO والاحتفاظ بالنسخ، وجهة النسخ الخارجية ومسؤول استعادتها.

### 3.2 بيانات الترخيص

- يسلّم المورد مفتاحًا موقّعًا رقميًا مرتبطًا بالعميل والنسخة/الوحدات والمدة والحصص المتفق عليها.
- لا تُنشئ مفاتيح التوقيع الخاصة أو تعدّل مفتاح التحقق المضمن؛ إصدار الترخيص مسؤولية المورد.
- ضع قيمة `LICENSE_KEY` في مخزن الأسرار أو ملف البيئة المحمي قبل أول تشغيل إنتاجي. بعض إصدارات الحزمة تسمح بالتفعيل من **إعدادات النظام ← الترخيص والإصدار**؛ اتبع تعليمات الإصدار المسلّم.
- تحقّق من اسم العميل، edition، تاريخ الانتهاء والوحدات والحصص في واجهة الترخيص بعد الإقلاع.
- النسخ المعزولة عن الإنترنت تحتاج إعدادًا متوافقًا مع الترخيص المسلّم. لا تفترض أن كل نسخة تسمح بالتفعيل دون اتصال؛ نسّق ذلك مسبقًا.
- نقل الآلة أو تغيير بصمة العتاد قد يتطلب إعادة تفعيل من المورد. لا تحذف ملف/بيانات التفعيل أو تنسخها إلى خادم آخر إلا وفق إجراء معتمد.

### 3.3 إنشاء الأسرار وتخزينها

أنشئ أسرارًا مستقلة وعشوائية لكل عميل وبيئة. مثال توليد من Node.js:

```bash
# مفتاح AES-256 مشفر بصيغة hex (64 خانة)
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# أسرار عشوائية بصيغة base64url (استخدم قيمة منفصلة لكل متغير)
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

على PowerShell يمكن استخدام:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

القيم المطلوبة عادةً في إعداد الإنتاج:

| المتغير | الغرض/القاعدة |
|---|---|
| `POSTGRES_PASSWORD` | كلمة مرور قاعدة البيانات. |
| `JWT_SECRET` | سر جلسات/رموز المصادقة؛ 32 حرفًا آمنًا على الأقل. |
| `ENCRYPTION_KEY` | مفتاح بيانات AES-256، 64 خانة hex. لا تغيّره عشوائيًا بعد إدخال البيانات؛ تدويره إجراء صيانة خاص. |
| `BLIND_INDEX_KEY` | مفتاح فهرسة بحث منفصل؛ لا تغيّره دون إجراء إعادة بناء/ترحيل موثق. |
| `BACKUP_ENCRYPTION_KEY` | مفتاح مستقل لنسخ قاعدة البيانات المشفرة، 64 خانة hex. فقدانه يمنع فك النسخ. |
| `ORTHANC_PASSWORD` | كلمة مرور Orthanc قوية وفريدة. |
| `PACS_WEBHOOK_SECRET` | سر توقيع الاتصالات بين Orthanc وAPI؛ قيمة مستقلة. |
| `LICENSE_KEY` | الترخيص الموقع الذي يقدمه المورد. |

احفظ نسخة استرداد مشفرة من الأسرار في خزنة مؤسسية منفصلة عن الخادم والنسخ اليومية. قيّد الوصول حسب الدور وسجّل عمليات الوصول. لا ترسل الأسرار بالبريد أو المحادثات، ولا تضعها في Git أو لقطات الشاشة أو سجلات التذاكر. تدوير `ENCRYPTION_KEY` أو `BLIND_INDEX_KEY` ليس تغيير كلمة مرور عاديًا؛ راجع [دليل تدوير المفاتيح](runbooks/KEY_ROTATION.md) وخذ نسخة قابلة للاستعادة أولًا.

## 4. تثبيت Linux وتشغيل Compose

### 4.1 تجهيز الخادم

1. ثبّت توزيعة Linux مدعومة ومحدثة (Ubuntu Server LTS أو Debian أو توزيعة المؤسسة المعتمدة).
2. أنشئ مستخدم خدمة غير تفاعلي، وثبّت Docker Engine وDocker Compose v2 من مستودع Docker الرسمي.
3. أنشئ قرصًا/نظام ملفات دائمًا وراقب المساحة. لا تضع قواعد البيانات أو صور DICOM على قرص مؤقت أو volume ephemeral.
4. قيّد SSH إلى شبكة الإدارة، استخدم مفاتيح دخول، فعّل الجدار الناري وتحديثات أمن نظام التشغيل.
5. استلم حزمة الإصدار من قناة المورد الموثوقة وتحقق من رقم الإصدار/الـchecksum أو التوقيع إن تم توفيره. لا تستخدم فرع التطوير أو `latest` في بيئة العميل.

مثال تثبيت Docker Engine وCompose Plugin على Ubuntu/Debian من المستودع الرسمي (راجع وثائق Docker الرسمية لاختيار التوزيعة والإصدار المناسبين):

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
docker --version
docker compose version
```

على Debian استخدم مسار مستودع Debian الرسمي بدل `linux/ubuntu` في الأوامر أعلاه. لا تضف حسابات المستخدمين العامة إلى مجموعة `docker`؛ صلاحية Docker تعادل عمليًا صلاحية root. استخدم حساب تشغيل إداري محدودًا مع `sudo` أو آلية تفويض مؤسسية.

### 4.2 تجهيز الإعداد

ضع ملفات الإصدار في مجلد مخصص، مثل `/opt/viara/releases/<version>`، واستخدم مسارًا ثابتًا للبيانات والإعدادات وفق الحزمة المعتمدة. لا تفترض أن تغيير مجلد الإصدار يحافظ على volumes إلا إذا بقي `COMPOSE_PROJECT_NAME` وملف Compose/مسارات volumes ثابتة.

1. انسخ القالب إلى `.env`، ثم استبدل **كل** القيم التوضيحية.
2. اضبط:
   - `NODE_ENV=production`
   - `CLIENT_URL` و`PORTAL_CLIENT_URL` إلى عناوين HTTPS الفعلية.
   - `PORTAL_PUBLIC_URL` إلى أصل البوابة العام. ابنِ واجهة الموظفين بالقيمة `VITE_OHIF_URL=/pacs-viewer/`، ووجّه reverse proxy هذا المسار إلى خدمة OHIF على مضيف تطبيق الموظفين نفسه؛ إعداد الواجهة يُخبز داخل الصورة ولا يتغير بتعديل `.env` عند التشغيل. يجب أن تحتوي صورة OHIF المعتمدة ملفات VIARA المخصصة، وأن يستخدم `CLIENT_URL` أصل HTTPS الدقيق دون مسار. لا تستخدم أصل OHIF مختلفًا لأن مصادقة الجلسة مقيدة بأصل التطبيق.
   - `ALLOWED_ORIGINS` إلى origins الدقيقة المسموح بها، مفصولة بفواصل وبصيغة HTTPS، دون wildcard.
   - `WEBAUTHN_ORIGIN` إلى origin HTTPS حرفي و`WEBAUTHN_RP_ID` إلى اسم المضيف أو نطاقه الأب المناسب. هذان مطلوبان في وضع الإنتاج وفق مدقق الإعدادات.
   - بيانات قاعدة البيانات، المفاتيح، كلمة مرور Orthanc، سر webhook، الترخيص، وعناوين PACS.
   - إعداد bind للمنافذ بحيث تكون الواجهات/API/DB/Orthanc REST محلية أو خلف proxy؛ خصّص DICOM لعنوان/شبكة الأجهزة فقط.
3. عيّن صلاحيات ملف `.env` إلى مالك الخدمة فقط (مثل `chmod 600 .env` على Linux)، ولا ترفعه إلى Git.
4. راجع الحزمة المسلّمة: بعض القوالب تحمل عناوين HTTP محلية للتجربة، لكنها غير صالحة لوضع الإنتاج؛ يتطلب backend في الإنتاج عناوين HTTPS محددة.

### 4.3 فحص وتشغيل أول مرة

من جذر حزمة Compose المعتمدة:

تحقق أولًا من أن كل `build.context` وملفات bind-mount المشار إليها في Compose موجودة ضمن محتوى الإصدار الذي استلمته. بعض ملفات Compose في المستودع تبني من مجلدات شقيقة مثل `../backend` و`../frontend`، ولذلك لا يكفي نسخ ملف Compose وحده إلى خادم العميل. إذا كانت الحزمة تعتمد صورًا جاهزة، يجب أن يحدد المورد أسماء الصور ووسومها وطريقة سحبها بدل البناء من مصدر غير موجود.

```bash
docker compose config --quiet
docker compose pull
# إذا كانت الحزمة تتطلب البناء من ملفات المصدر:
docker compose build --pull

docker compose up -d
docker compose ps
docker compose logs --tail=200 postgres migrate clamav backend frontend portal orthanc ohif
```

استخدم `pull` أو `build` حسب آلية التسليم؛ لا تنفذ الاثنين عشوائيًا إذا كانت صور العميل موقّعة/مسبقة البناء. في Compose الجذر للمستودع، خدمة `migrate` تسبق backend عبر شروط الاعتماد. الحزم الأخرى قد تختلف؛ اتبع تعليمات الإصدار ولا تشغّل migrations يدويًا قبل قراءة دليل الإصدار.

تحقق من أن PostgreSQL وClamAV والخدمات التي يتضمنها الترخيص أصبحت healthy، وأن migration اكتملت بنجاح، ثم اختبر من داخل الشبكة:

```bash
curl -fsS http://127.0.0.1:3000/health/ready
docker compose ps
```

قد لا يكون منفذ API مكشوفًا على المضيف في إعداد الإنتاج؛ عندئذ نفّذ اختبار الجاهزية من داخل حاوية backend أو من شبكة التطبيق. لا تفتح المنفذ لمجرد تنفيذ الاختبار. اختبر تسجيل الدخول بحساب أولي تم تسليمه/تهيئته بطريقة آمنة، غيّر كلمة المرور، أنشئ حسابات شخصية بصلاحيات مناسبة، ثم أكمل فحص قبول العميل في القسم 9.

### 4.4 تشغيل على شبكة محلية مغلقة

- عيّن DNS داخليًا وشهادة TLS من مرجع موثوق لأجهزة الموظفين؛ الشهادة ذاتية التوقيع غير الموثوقة ستعطل ميزات المتصفح مثل WebAuthn.
- اجعل واجهة الموظفين والبوابة خلف HTTPS حتى لو لم يكن لهما عنوان إنترنت عام. اسمح للبوابة داخليًا فقط عند عدم الحاجة لنشر عام.
- لا تحتاج نسخة الترخيص بالضرورة إلى اتصال خدمة الترخيص الخارجية؛ اضبط `LICENSE_PING_ENABLED` وفق متطلبات الإصدار واتفاق الترخيص بعد التنسيق مع المورد.
- اسمح باتصال أجهزة التصوير إلى منفذ DICOM من VLAN المصرح فقط. اختبر C-ECHO ثم إرسال دراسة تجريبية غير حقيقية، والتحقق من ظهورها في Orthanc والـRIS.
- حدّد طريقة نقل التحديثات إلى الشبكة المعزولة (وسيط موثوق، فحص malware، تحقق checksum/توقيع، سجل الاستلام) قبل أول تحديث.

مثال مبدئي لجدار UFW على Linux؛ استبدل الشبكات والعناوين بقيم العميل قبل التطبيق، وتأكد من وجود جلسة/مسار إدارة بديل كي لا تقطع اتصال SSH:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from <ADMIN_SUBNET_CIDR> to any port 22 proto tcp
sudo ufw allow from <STAFF_SUBNET_CIDR> to any port 443 proto tcp
sudo ufw allow from <MODALITY_SUBNET_CIDR> to any port 4242 proto tcp
sudo ufw status verbose
sudo ufw enable
```

إذا كان reverse proxy على خادم مختلف، اسمح من عنوانه فقط إلى منافذ الواجهة/البوابة/API الخلفية المطلوبة، لا إلى قاعدة البيانات أو Orthanc REST. راجع أثر سياسات UFW مع قواعد Docker؛ نشر Docker للمنافذ قد يتجاوز بعض قواعد UFW. استخدم جدار الشبكة/host firewall المدعوم، وتحقق من الوصول من جهاز غير مصرح به بعد النشر.

### 4.5 فحص إعداد Compose والتخزين قبل الإطلاق

قبل أول تشغيل أو تحديث، افحص الإعداد النهائي بعد دمج `.env`، لا ملف YAML وحده:

```bash
docker compose config --quiet
docker compose config
docker compose ps
docker volume ls
```

`docker compose config` قد يطبع قيم أسرار مدمجة؛ لا تحفظ مخرجاته في تذكرة أو ملف عام ولا تشاركها. استخدم `--quiet` للفحص المعتاد. تأكد من الآتي يدويًا في إعداد الإصدار المعتمد:

- منافذ PostgreSQL وOrthanc REST غير منشورة على جميع واجهات المضيف.
- واجهات الويب لا تستقبل HTTP غير مشفر مباشرة من شبكات المستخدمين؛ ضعها خلف TLS proxy أو استخدم الآلية المعتمدة للحزمة.
- منفذ DICOM مربوط إلى واجهة شبكة الأجهزة ومسموح فقط من عناوين modality المحددة.
- أسماء volumes ومشروع Compose ومساراتها ثابتة بين إصدارات العميل. لا تغيّر `COMPOSE_PROJECT_NAME` أو اسم المشروع أثناء التحديث دون خطة نقل volumes معتمدة.
- بيانات PostgreSQL وOrthanc والرفع والنسخ موجودة على تخزين دائم، مع مراقبة مساحة القرص وصلاحيات المجلدات.

**تنبيه خاص بملفات Compose الموجودة في المستودع:** إعداد حزمة `viara-production-package` يعرض بعض منافذ المضيف (ومنها PostgreSQL وواجهات HTTP) على نطاق أوسع من loopback افتراضيًا، ويضبط DICOM على `0.0.0.0`. اعتبره قالبًا يحتاج تقييد bind والجدار الناري قبل نشره، ولا تفترض أن إعدادات `docker-compose.yml` الجذر مطابقة له. الحزمة/الإصدار الذي يسلّمه المورد هو المرجع، ويجب فحص `docker compose config` عليه قبل تشغيله.

### 4.6 بدء الخدمة وإيقافها ومراقبتها

نفّذ الأوامر من المجلد الذي يحتوي ملف Compose المعتمد وملف `.env` الصحيح؛ لا تنفذها من مجلد تطوير آخر بالخطأ.

```bash
# تشغيل/تطبيق حالة Compose الحالية
docker compose up -d

# الحالة والصحة
docker compose ps
docker compose ps --all

# سجلات محدودة لخدمة محددة؛ نقّحها قبل مشاركتها
docker compose logs --tail=200 backend

# إيقاف منظم مع الاحتفاظ بالـvolumes
docker compose down
```

بعد إعادة تشغيل الخادم، تعود الحاويات للعمل تلقائيًا إذا كان Compose مضبوطًا بسياسة `restart: unless-stopped` وكان Docker daemon مفعّلًا عند الإقلاع؛ تحقق من ذلك على الحزمة الفعلية ولا تعتبر رسالة نجاح سكربت التشغيل دليلًا على جاهزية كل المكونات. بعد `down` أعد التشغيل بـ`up -d`. لا توقف PostgreSQL بالقوة أثناء كتابة البيانات.

لإعادة تشغيل خدمة واحدة فقط بعد تغيير إعدادها، استخدم `docker compose restart <service>` بعد فهم أثر التغيير؛ تغييرات متغيرات البيئة أو بناء الصورة غالبًا تتطلب إعادة إنشاء الحاوية (`docker compose up -d <service>`) لا مجرد restart. لا تعِد تشغيل Orthanc أو PostgreSQL أثناء عمليات تخزين/ترحيل دون نافذة معتمدة.

> حزمة مساحة العمل قالب غير معتمد للتسليم. سكربت Linux الحالي يفرض مراجع الصور المثبتة، وينتظر الخدمات التي لديها health check، ثم يفشل مع عرض حالة Compose إذا لم تصبح سليمة خلال المهلة. لا يتحقق من جاهزية Orthanc/DICOM؛ افحص PACS منفصلًا. لا تطبع السكربتات روابط localhost للمستخدمين، لأن منافذ التطبيقات مربوطة بـloopback افتراضيًا؛ استخدم نطاق HTTPS وreverse proxy معتمدين. على Windows Server شغّل الحاويات داخل Linux VM مدعومة، ولا تعتبر `start.bat` بديلًا عن إعداد المضيف ومسارات bind mounts.

## 5. تشغيل عميل Windows

### المسار الموصى به للإنتاج

1. جهّز Windows Server مع Hyper-V أو استخدم منصة افتراضية معتمدة.
2. أنشئ Linux VM مخصصة لـ VIARA مع أقراص ثابتة منفصلة/مخطط لها لبيانات التطبيق وPACS والنسخ.
3. نفّذ خطوات Linux السابقة **داخل الـVM**.
4. استخدم Nginx أو reverse proxy مؤسسيًا داخل Linux VM. يمكن تمرير DNS من Windows/DNS المؤسسة إلى عنوان VM. إذا فرضت سياسة المؤسسة استخدام IIS على Windows كواجهة TLS، اختبر الاتصال بين IIS والـVM، websocket/headers، حجم رفع الملفات، ومسارات الواجهة والبوابة قبل الإنتاج؛ لا تجعل IIS يفتح منافذ البيانات مباشرة.
5. اسمح في جدار Windows والشبكة فقط بـ HTTPS من شبكات المستخدمين، وDICOM من VLAN الأجهزة، وSSH/الإدارة من شبكة تقنية المعلومات. لا تسمح بـ5432 أو Orthanc REST من شبكات المستخدمين أو الإنترنت.
6. فعّل نسخًا احتياطية لـ VM/الأقراص بتنسيق متوافق مع قواعد البيانات، ولا تعتمد على snapshot وحيد كنسخة احتياطية.

**غير موصى به:** تشغيل backend وOrthanc وClamAV كخدمات Windows أصلية أو استخدام Windows containers؛ ملفات التشغيل وحاويات النظام الحالية مبنية أساسًا على Linux. Windows 10/11 أو Docker Desktop مناسب للاختبار المحلي فقط، وليس توصية إنتاج لمستشفى.

## 6. الاستضافة السحابية والاستضافات الأخرى

### 6.1 VM سحابية

النمط الأقرب إلى تشغيل الموقع الداخلي هو VM Linux خاصة مع Docker Compose. استخدم شبكة خاصة، قواعد firewall/security groups دقيقة، TLS، تشفير أقراص، تخزينًا دائمًا لـPostgreSQL وOrthanc والرفع والنسخ، ومراقبة خارجية. اجعل قاعدة البيانات غير عامة. وفر اتصالًا خاصًا من أجهزة التصوير عبر VPN أو شبكة المؤسسة؛ لا تمرر DICOM عبر الإنترنت العام دون تصميم أمني معتمد.

### 6.2 خدمات قواعد بيانات مُدارة أو منصات الحاويات

لا تفترض أن Compose الحالي يتصل تلقائيًا بـ RDS/Cloud SQL أو أن PaaS يحفظ volume الخاص بـ Orthanc. قبل اعتماد هذا النمط يلزم تصميم موثق لـ:

- PostgreSQL TLS، الشبكة، مستخدم/صلاحيات migrations، backup/restore والتوافق مع إعدادات المنتج.
- تخزين Orthanc/DICOM والرفع وبيانات الفهرس، التشفير والاستعادة واتساق النسخ.
- الأسرار، health checks، WebSocket، الملفات الكبيرة، المنافذ وDICOM.
- ترحيل قاعدة البيانات عند التوسع والرجوع عن الإصدارات.

Kubernetes يتطلب manifests/Helm وStorageClass وSecrets وIngress وسياسة ترقية/rollback ملائمة؛ مثال deployment في README **ليس** بديلًا عن هذه العناصر. اطلب مراجعة واعتمادًا من المورد قبل استخدام Kubernetes أو PaaS أو استضافة متعددة المناطق.

### 6.3 النطاقات والـ reverse proxy

سواء كان Nginx أو IIS أو HAProxy أو مزودًا سحابيًا، يجب أن:

- ينهي TLS بشهادة موثوقة، ويحوّل HTTP إلى HTTPS إن كان HTTP مطلوبًا للشهادة/التحويل فقط.
- يوجّه `/api` إلى backend، الواجهة إلى staff frontend، أصل بوابة المرضى إلى portal، وOHIF حسب طريقة الإصدار.
- يمرر `Host` و`X-Forwarded-Proto` وIP الحقيقي بطريقة موثوقة، ويدعم WebSocket عند استخدامه.
- يضبط حد رفع مناسبًا للملفات/الدراسات، وtimeouts للأعمال الطويلة دون تعطيل حدود الخدمة.
- لا ينشر `/metrics` أو لوحة Orthanc أو PostgreSQL للعامة. لا تنسخ إعدادات proxy من أمثلة عامة دون اختبار CSP وتدفق البوابة وتضمين OHIF.

راجع [مرجع TLS وReverse Proxy](REVERSE_PROXY_TLS.md) وكيّف الإعداد مع مسارات الحزمة وإصداراتها. عند وجود نطاقين مختلفين (staff/portal)، أدرج origin كل منهما بدقة في إعدادات CORS/WebAuthn وفق التصميم المعتمد.

### 6.4 الوصول عن بُعد (Remote Access)

للفصل الصارم بين البوابة العامة والوصول السريري، استخدم حزمة النشر الجاهزة في [`deploy/remote-access/`](../deploy/remote-access/README.md). تنفّذ ثلاث طبقات ثقة:

| الطبقة | الجمهور | آلية الوصول | الملف |
|---|---|---|---|
| عامة | المرضى/الأطباء المحوّلون | Cloudflare WAF/Tunnel (بلا منفذ داخل) | `deploy/remote-access/nginx/portal-edge.conf` |
| سريرية | أخصائيو الأشعة (قائمة العمل + OHIF) | WireGuard + mTLS إلزامي | `deploy/remote-access/nginx/clinical-edge.conf` |
| محلية | أجهزة التصوير وقاعدة البيانات وOrthanc | LAN/VLAN فقط | `docker-compose.yml` + ACL |

**قواعد غير قابلة للتفاوض:** لا يُنشر OHIF على الإنترنت إطلاقًا؛ يبقى على نفس أصل تطبيق الموظفين تحت `/pacs-viewer/`؛ البوابة العامة تُرجع 404 لمسارات العارض والإدارة؛ ومنفذ DICOM 4242 مربوط بواجهة الأجهزة فقط. للتحقق: `deploy/remote-access/scripts/verify-remote-access.sh`.

## 7. الحماية التشغيلية والخصوصية

1. **تقليل التعرض:** جدار ناري افتراضي الرفض؛ HTTPS فقط للمستخدمين؛ DICOM محصور بمصادر الأجهزة؛ لا PostgreSQL أو Orthanc REST على الإنترنت.
2. **حسابات وصلاحيات:** حساب منفصل لكل موظف، أقل صلاحية لازمة، تفعيل MFA/passkey حيث تسمح السياسة، تعطيل الحسابات المغادرة، ومراجعة الأدوار دوريًا. لا تشارك حساب المدير أو بيانات الدخول التجريبية.
3. **أسرار ومفاتيح:** خزنة أسرار، صلاحيات قراءة محدودة، نسخ استرداد خارجية، وعدم تسجيل المفاتيح. احتفظ بمفاتيح التشفير نفسها اللازمة لفك البيانات والنسخ؛ تشفير backup بمفتاح محفوظ فقط داخل الخادم لا يحمي من فقدان الخادم.
4. **تحديثات:** حدّث نظام التشغيل وDocker وimages من مصدر موثوق بعد اختبار staging؛ ثبّت نسخًا محددة، لا تستخدم `latest` للإنتاج.
5. **مكافحة البرمجيات الضارة:** أبق ClamAV مفعّلًا ومحدث التواقيع؛ لا تتجاوز فحص الملفات لتجاوز مشكلة تشغيلية دون تقييم مخاطر وموافقة.
6. **PACS:** Orthanc REST يبقى داخليًا، كلمة مروره قوية، DICOM محصور، وأقراص DICOM مشفرة/محكومة بالوصول. افصل صلاحيات مستخدمي الأجهزة عن إدارة الخادم.
7. **خدمات خارجية والذكاء الاصطناعي:** لا ترسل بيانات تعريفية أو صور مرضى إلى مزود خارجي إلا بعد تقييم قانوني/أمني واعتماد العقد وموقع المعالجة وسياسة الاحتفاظ والإعدادات. اترك التكامل معطلًا إلى حين الاعتماد.
8. **السجلات:** اجمع سجلات التشغيل والأمان دون تسجيل كلمات المرور أو الرموز أو بيانات مرضى زائدة. امنح الوصول للمخولين وحدد الاحتفاظ والتصدير.
9. **الامتثال:** التشفير أو وجود audit trail لا يعني وحده الامتثال لأي تشريع. يحدد العميل ومستشاره القانوني/الأمني ضوابط الخصوصية، الموافقات، الإقامة الجغرافية للبيانات، واحتفاظ السجلات.

### 7.1 تجهيز الحسابات قبل فتح النظام للمستخدمين

1. استلم من المورد وسيلة تهيئة المدير الأول عبر قناة آمنة، أو استخدم آلية onboarding المعتمدة للإصدار. لا تفترض وجود حساب افتراضي واحد لكل الحزم، ولا تستخرج كلمة مرور من README أو `.env` تجريبي.
2. أنشئ حسابًا إداريًا شخصيًا لمسؤول العميل، ثم تحقق من الدخول والصلاحيات. غيّر كلمة المرور المؤقتة مباشرة، ولا ترسلها لمجموعة مستخدمين.
3. أنشئ حسابات الموظفين بأسمائهم وهوياتهم المؤسسية، وحدد الدور وأقل صلاحيات تشغيلية لازمة. لا تستخدم حساب Developer أو Admin كحساب يومي.
4. فعّل وسائل المصادقة الإضافية المتاحة وفق سياسة المؤسسة، وسجّل إجراءات الاستعادة الآمنة للحسابات الإدارية.
5. اختبر تعطيل حساب اختبار ومراجعة سجل التدقيق، ثم وثّق من يملك صلاحية إنشاء الحسابات وتغيير الأدوار ومراجعتها.

**بوابة جاهزية إصدار العميل:** جرى تحديث مجلد `viara-production-package` في مساحة العمل لاستخدام صور مسبقة البناء دون build contexts، مع مراجع صور كاملة مطلوبة، وتأمين binds الافتراضية على loopback، ومزامنة migrations وملفاتها مع manifest المصدر، وإزالة بيانات الدخول الافتراضية من تعليمات التشغيل. مع ذلك، لم تُدخل مراجع إصدار فعلية ولم تُسحب الصور ولم يُنشأ أرشيف تسليم جديد، كما لم يُختبر النشر على staging؛ لذلك تظل هذه التغييرات إعدادًا مرجعيًا فقط وليست اعتمادًا للإنتاج. احتوى الأرشيف المحلي السابق الذي تمت مراجعته ملف `.env` وترخيصًا، فلا تستخدمه ولا تسلّمه. قبل أي إصدار، يجب مراجعة منافذ DICOM وإعداد reverse proxy والجدار الناري، والتأكد من عناوين الواجهة والبوابة وOHIF المبنية داخل صورة frontend، والتحقق من الأسرار والترخيص وإجراء الفحص الأمني والتشغيلي على الأثر الدقيق الذي سيُسلّم.

## 8. النسخ الاحتياطي والاستعادة

### 8.1 ما الذي يجب نسخه؟

نسخ PostgreSQL لا يحتوي تلقائيًا على صور PACS أو كل ملفات الرفع أو إعدادات/أسرار الخادم. ضع خطة مستقلة ومتسقة تشمل:

- PostgreSQL وفق إعداد `BACKUP_MODE=postgres` وجدولة النسخ المشفرة (`BACKUP_ENCRYPTION_KEY`).
- Volume تخزين Orthanc/DICOM ومؤشراته؛ استخدم snapshot/آلية متسقة مع طريقة تخزين الإصدار، واختبر استعادة الصور.
- ملفات الرفع والمستندات، إعدادات العميل غير السرية، ونسخة آمنة من ملفات الترخيص/التفعيل حيث يسمح الترخيص.
- ملفات الإعداد والمفاتيح في خزنة منفصلة؛ لا تضعها بجوار النسخ غير المشفرة.

في Compose الجذر، النسخ المجدول لقاعدة البيانات مضبوط في الخدمة على وضع PostgreSQL يوميًا عند 02:00 UTC والاحتفاظ الافتراضي 30 يومًا/30 ملفًا. تحقق من إعداد إصدار العميل ومن نجاح النسخ ونسخها خارج الخادم. هذا الجدول وحده يعني احتمال فقد ما يصل إلى يوم من تغييرات قاعدة البيانات؛ غيّره وفق RPO المعتمد. لا يعني أن صور DICOM تم نسخها.

> **نطاق نسخة الحزمة:** `viara-production-package/scripts/backup.sh` يستدعي خدمة المنتج لإنشاء نسخة PostgreSQL مشفرة ومتحققًا منها. لا يحتوي هذا الملف وحده صور DICOM أو uploads أو worklists أو volume `license_data`؛ أضفها إلى خطة متسقة ومشفرة وخارج الخادم، واستعدها مع قاعدة البيانات ومفاتيحها في اختبار دوري.

### 8.2 اختبارات الاستعادة

- نفّذ استعادة تجريبية إلى بيئة منفصلة قبل التشغيل الفعلي، ثم دوريًا (ربع سنوي نقطة بدء) وبعد تغييرات كبيرة.
- تحقّق من السجلات وعدد السجلات الأساسية، فك تشفير معلومات المريض، البحث، الدخول، الفواتير، واسترجاع عينة صور DICOM.
- احذف النسخة المفكوكة مؤقتًا وفق سياسة المؤسسة؛ تحتوي PHI.
- وثّق زمن الاستعادة الفعلي وقارنه بـ RTO.

اتبع [Runbook استعادة PostgreSQL](runbooks/RESTORE.md)؛ وهو يوضح أن نسخ قاعدة البيانات لا تستعيد volume صور Orthanc وحدها.

## 9. فحص القبول بعد التثبيت

قبل تسليم النظام للمستخدمين، نفّذ وسجّل كل بند:

- [ ] تم توثيق رقم إصدار الحزمة ومصدرها، والتحقق من checksum/توقيع إن توفر.
- [ ] تأكد مسؤول الإصدار من عدم وجود حسابات/كلمات مرور تجريبية أو أسرار ثابتة أو نصوص تعرض بيانات الدخول في الحزمة وملفات السجل.
- [ ] `docker compose config --quiet` ينجح، وجميع الخدمات المطلوبة تعمل وتصبح healthy.
- [ ] ترحيلات قاعدة البيانات اكتملت، وحالة الترخيص والعميل والوحدات صحيحة.
- [ ] الواجهة والبوابة تفتحان عبر HTTPS من جهاز مستخدم، والشهادة موثوقة.
- [ ] تسجيل الدخول والخروج وحساب مدير جديد يعملان، وتم تغيير أي كلمة مرور ابتدائية.
- [ ] origins وWebAuthn والمصادقة لا تظهر أخطاء متصفح/CORS.
- [ ] قاعدة البيانات وOrthanc REST غير متاحين من شبكة المستخدمين أو الإنترنت.
- [ ] DICOM C-ECHO وإرسال دراسة اختبار مصرح بها يعملان من VLAN الأجهزة.
- [ ] فحص ClamAV يعمل؛ تم اختبار رفع ملف آمن مسموح به فقط.
- [ ] تم إنشاء backup مشفر والتحقق من وجوده ونسخه إلى وجهة منفصلة.
- [ ] استعيدت نسخة تجريبية في بيئة معزولة، بما في ذلك عينة PACS، أو وُثّق سبب عدم جاهزية الاستعادة.
- [ ] التنبيهات لمشكلات مساحة القرص/فشل النسخ/توقف الخدمات مفعلة ومسؤولها معروف.
- [ ] تم اعتماد قائمة مسؤولي النظام، جهات الدعم، RPO/RTO، نافذة الصيانة وإجراء الطوارئ.
- [ ] تم إنشاء حسابات شخصية بصلاحيات معتمدة، وإلغاء/تغيير كل اعتماد مؤقت قبل فتح الخدمة للمستخدمين.

## 10. إجراء تحديث إصدار جديد

### قبل التحديث

1. استلم إصدارًا مرقمًا من المورد، وراجع ملاحظات الإصدار والتوافق ومتطلبات الترحيل وموعد الدعم.
2. جرّب التحديث على staging مماثل للإنتاج (نفس إعداد TLS والتخزين والترخيص قدر الإمكان)، مع نسخة بيانات منزوعة الهوية إن احتجت.
3. أعلن نافذة الصيانة وحدد مسؤول النشر والرجوع. امنع تغييرات تشغيلية أثناء النسخ/التحويل حسب خطة العميل.
4. خذ backup مشفرًا لقاعدة البيانات، snapshot/نسخة للـDICOM والملفات، واحفظ نسخة الإعدادات ومفاتيحها بأمان. تحقق من حجم وتاريخ النسخ.
5. سجّل الإصدار الحالي ووسوم الصور ومخرجات `docker compose ps` وحالة الخدمات، وتأكد من وجود مساحة كافية.

### التنفيذ

استخدم مجلد إصدار جديدًا أو آلية النشر التي يحددها المورد. لا تستبدل ملفات الإصدار العامل قبل ضمان حفظ إعداد العميل وبياناته الدائمة.

```bash
# من مجلد الإصدار الموثوق بعد إعداد أسرار البيئة
docker compose config --quiet
docker compose pull
# أو، إذا كانت تعليمات الإصدار تقتضي البناء من المصدر/ملفات الحزمة:
docker compose build --pull

# قبل ترقية migrations اتبع ملاحظات الإصدار.
# استخدم الأمر المنفصل فقط إذا كان دليل الإصدار يطلبه:
docker compose run --rm migrate

docker compose up -d
docker compose ps
docker compose logs --tail=200 migrate backend frontend portal orthanc
```

في Compose الذي يعرّف `migrate` كاعتماد إلزامي للـbackend، قد يشغّل `up -d` مرحلة migration تلقائيًا؛ لا تشغّلها بالتوازي من نافذتين. لا تشغل `node database/migrate.js --fresh` على بيانات العميل؛ خيار `--fresh` يعيد إنشاء المخطط وقد يؤدي لفقد البيانات.

### بعد التحديث

- تحقق من اكتمال migrations وhealth checks، ثم نفّذ بنود فحص القبول المتعلقة بالدخول والبحث والمالية والتقارير والرفع وDICOM/صور سابقة.
- راقب السجلات ومؤشرات الأداء وفشل النسخ خلال فترة المراقبة المتفق عليها.
- لا تحذف الإصدار السابق أو النسخ الاحتياطية حتى اعتماد التحديث وانتهاء فترة الرجوع.
- سجّل رقم الإصدار، تاريخ التحديث، المنفذ، نتيجة الاختبارات، وملاحظات العميل.

### الرجوع عند الفشل

1. أوقف/اعزل الإصدار الجديد حسب تعليمات الطوارئ، واحفظ السجلات.
2. ارجع إلى صور/حزمة الإصدار السابق **فقط إذا أكدت ملاحظات التحديث توافق قاعدة البيانات بعد migration**.
3. إذا كان المخطط غير متوافق أو حدث تلف بيانات، استعد PostgreSQL والـDICOM/الملفات من النسخ المتطابقة المأخوذة قبل التحديث، وفق runbooks. استعادة DB وحدها قد تسبب عدم تطابق مع صور PACS.
4. أعد فحوص الصحة وسير العمل، ثم وثّق سبب الفشل وتواصل مع دعم المورد.

لا تفترض أن migrations قابلة للعكس أو أن إعادة تشغيل صورة قديمة تعكس تغيير مخطط قاعدة البيانات. قرار الاستعادة قد يعيد بيانات أحدث من آخر backup إلى الوراء؛ خذ موافقة مالك البيانات وسجّل الأثر.

### تحديث من Windows عند استضافة VIARA على Linux VM

شغّل Docker Compose وأوامر التحديث **داخل Linux VM**. يمكن لمسؤول Windows الاتصال عبر SSH من PowerShell، ثم متابعة نفس الخطوات أعلاه في جلسة Linux:

```powershell
ssh <DEPLOY_USER>@<LINUX_VM_ADDRESS>
```

قبل التحديث احفظ ملفات الإصدار الموثوقة في مجلد إصدار جديد داخل VM، ثم ادخل إلى المجلد الذي يحتوي ملف Compose الصحيح وتحقق من `COMPOSE_PROJECT_NAME` وملف البيئة الدائم. بعد اعتماد staging والنسخة الاحتياطية، شغّل أوامر التحديث في القسم 10. لا تنفذ `docker compose down -v`، ولا تحذف مجلد الإصدار السابق أو volumes لتوفير مساحة قبل التحقق من النسخ والرجوع.

بعدها يمكن من PowerShell التحقق من شهادة HTTPS ونقطة الجاهزية المنشورة:

```powershell
Invoke-WebRequest -Uri "https://<VIARA_HOST>/health/ready" -Method Get
```

إذا كان reverse proxy لا يمرر `/health/ready` من النطاق العام، نفّذ التحقق من داخل الـVM أو من شبكة الإدارة بدل فتح منفذ backend للعامة.

## 11. التشغيل اليومي ومسؤوليات العميل

| التكرار | الإجراء |
|---|---|
| يوميًا | مراجعة صحة الحاويات، فشل النسخ، مساحة PostgreSQL/PACS، التنبيهات، ونطاقات DICOM غير المعتادة. |
| أسبوعيًا | التحقق من اكتمال نسخ خارج الموقع وحداثتها، تحديث تواقيع ClamAV، ومراجعة الحسابات المقفلة/غير المستخدمة. |
| شهريًا | مراجعة الصلاحيات، مساحة النمو، انتهاء الشهادات والترخيص، نجاح مزامنة الوقت، وخطة السعة. |
| ربع سنوي أو حسب سياسة العميل | تجربة استعادة كاملة، مراجعة الوصول الخارجي وFirewall، اختبار حسابات الطوارئ، ومراجعة RPO/RTO. |
| كل إصدار | staging، backup، تحديث موثق، اختبارات قبول، وخطة rollback. |

### أوامر تشغيلية آمنة شائعة

```bash
docker compose ps
docker compose logs --tail=200 backend
docker compose logs --tail=200 postgres
docker compose restart backend
docker compose down
```

`docker compose down` يوقف الحاويات لكنه لا يزيل volumes عادةً. **لا تستخدم** `docker compose down -v` على نظام يحوي بيانات العميل؛ حذف volumes قد يمحو قواعد البيانات والصور. لا تحذف مجلدات التخزين أو النسخ يدويًا دون موافقة وخطة استعادة.

## 12. استكشاف الأعطال والتصعيد

| العرض | فحوص أولية آمنة | ما يجب عدم فعله |
|---|---|---|
| الحاوية تعيد التشغيل أو readiness تفشل | `docker compose ps` ثم `docker compose logs --tail=200 <service>`؛ راجع حالة PostgreSQL وClamAV والترخيص والـmigrations. أخفِ أي أسرار/بيانات مريض قبل مشاركة السجل. | لا تعطل التحقق من الإعداد أو الترخيص ولا تنشر سجلًا كاملًا يحوي بيانات حساسة. |
| فشل تسجيل الدخول بعد التحديث | تحقق من HTTPS ووقت النظام، صحة backend، إعدادات origin/cookie، وسجل المصادقة المنقح. | لا تمسح الجداول أو تغيّر مفاتيح التشفير كحل تجريبي. |
| فشل فك بيانات المرضى أو البحث بعد تبديل مفاتيح | أوقف التغييرات، استعد إعداد المفاتيح من الخزنة، وصعّد لمسؤول المفاتيح قبل أي كتابة إضافية. | لا تولّد `ENCRYPTION_KEY` أو `BLIND_INDEX_KEY` جديدة على قاعدة بيانات قائمة. |
| أجهزة التصوير لا تتصل | راجع IP الخادم، bind والمنفذ 4242، AE Title، مسار الشبكة وقواعد الجدار الناري من VLAN الأجهزة؛ اختبر C-ECHO وفق أداة الجهاز. | لا تفتح DICOM للعامة أو توسع ACL إلى كل الشبكات كاختبار. |
| فشل رفع مستند | افحص حجم الطلب المسموح في proxy، مساحة التخزين، جاهزية ClamAV وسجلات الرفع. | لا تعطل فحص الفيروسات ولا ترفع حد الحجم بلا تقدير. |
| فشل النسخ أو امتلاء القرص | تحقق من حالة scheduler، `BACKUP_DIR`، المساحة، صلاحيات الكتابة، مفتاح backup، ووجهة النسخ الخارجية. خذ نسخة تشغيلية وفق runbook عند الحاجة. | لا تحذف أقدم نسخة أو volume يدويًا قبل تأكيد نسخة خارجية قابلة للاستعادة. |
| تحديث غير سليم | أوقف النشر المتتابع، احفظ logs/الإصدار، اتبع rollback المتوافق مع migrations، وأشرك مسؤول قاعدة البيانات والمورد. | لا تستخدم migration `--fresh` أو استعادة DB وحدها دون النظر إلى DICOM والملفات. |

عند فتح تذكرة دعم، أرفق إصدار VIARA، نظام التشغيل/نسخة Docker، أوقات الحدوث والمنطقة الزمنية، أسماء الخدمات المتأثرة، حالة health checks، وأجزاء logs منقحة. لا ترسل `.env` أو مفاتيح أو أسماء/أرقام مرضى أو صور DICOM؛ استخدم قناة دعم آمنة عند طلب ملفات تشخيصية واعتمد موافقة مسؤول الخصوصية.
