تاريخ التنفيذ: 11 أكتوبر 2026. النتيجة: **نجاح الاختبار المالي المحدد؛ لا تمثل موافقة على الإنتاج السريري**.

## حدود التقييم

الاختبار يعمل على Windows Docker Desktop ومحرك Linux، باتصال HTTP محلي من داخل حاوية الخادم، وحساب مدير اصطناعي واحد. لا يغطي TLS أو الشبكة البعيدة أو الأجهزة المحمولة أو تحميل DICOM أو تعدد المستخدمين الحقيقي أو صلاحيات الكاشير. تجهيز الفواتير والوردية وتجاوز مرحلة تغيير كلمة المرور لأول دخول تم مباشرة في قاعدة اختبار جديدة؛ إنشاء الفاتورة وفتح الوردية من الواجهة غير مشمولين. الفواتير نقدية بلا مرضى أو فحوصات أو تأمين أو صبغة؛ لذلك لا يثبت الاختبار سلامة الدورة السريرية أو تسليم التقارير أو حالات الاسترداد والخصم.

لم يُعطّل محدد الطلبات، ولم يُفعّل PERF_TEST_MODE. يحمي الاختبار التنفيذ باشتراط تفعيل صريح، ثم التأكد من وجود المدير الاصطناعي وحده وخلو جداول المرضى والفواتير والمدفوعات والورديات قبل أي تجهيز. يُنشئ المشغّل مشروع Docker فريداً ويحذف حاوياته وأحجامه وحدها في النهاية. الترخيص ومفتاح التحقق المستخدمان اصطناعيان داخل إعدادات الاختبار، ولا يغيّران مفتاح المنتج.

ملاحظة على سيناريو الأداء القديم `04_billing_payment.js`: اختيار الفاتورة حسب رقم المستخدم قد يكرر الفاتورة بين المستخدمين. عندئذ قد يعتبر فحص زيادة عدد المدفوعات بمقدار واحد دفعات متزامنة صحيحة خطأً. الاختبار الجديد يتجنب ذلك بإسناد فاتورة مستقلة لكل مسار في قياس الأساس، ويختبر التنافس على فاتورة مشتركة في حالات منفصلة محددة.

## إعادة التنفيذ

يتطلب محرك Docker Linux جاهزاً وصور الحزمة المحلية وPython المستخدم في اختبار إعداد المدير. يُنفذ من جذر المشروع:

```powershell
$env:VIARA_RELEASE_TEST_PACKAGE_DIR = 'D:\VIARA\dist\client-release\staging-20261010-pg15-db1a574'
$env:VIARA_TEST_PAYMENT_LOAD = '1'
node scripts/verify-client-release-containers.cjs
```

لا تشغّل نسختين من مشغّل الحاويات بالتزامن؛ يستخدم الاختبار شبكة ثابتة `172.31.247.0/24`. لا توجّه المجلد إلى حزمة عميل تعمل فعلياً، ولا تنقل بيانات الاختبار أو مفتاح ترخيصه إلى موقع الإنتاج.

## القرار والتوصيات

**يظل النشر السريري NO-GO** وفق [مراجعة الجاهزية الحالية](FINAL_READINESS_AUDIT_2026-10-10_AR.md). نجاح التحصيل هنا لا يغلق فجوات توثيق إعطاء الصبغة، سياسة التجاوز الطارئ، الإقرار والتصعيد للنتائج الحرجة، سياسة الوصول للتقرير مع المديونية، وضمان إشعارات جاهزية التقرير. كما تسجل المراجعة فجوة فحص ClamAV في رفع PACS واتساع CSP؛ يلزم معالجة واختبار هذه المسارات على نسخة ثابتة.

الأولويات العملية:

1. إكمال الإصلاحات السريرية والأمنية الجارية، ومراجعتها واعتماد سياسة الموقع دون الخلط بين المتابعة الإدارية والإقرار السريري.
2. تجميد SHA جديد، بناء حزمة جديدة، وتشغيل اختبارات الترحيل والتحصيل والاستعادة وسير التقارير على صورها الفعلية؛ لا تعِد تسمية الحزمة السابقة باعتبارها تشمل التعديلات الجديدة.
3. اختبار حمل ممثل بعد تحديد عدد المستخدمين المتزامنين ومزيج الوظائف وحجم دراسات DICOM، مع مراقبة CPU/RAM/DB/الشبكة والكمون والأخطاء خلال مدة ممتدة.
4. تنفيذ استعادة على مضيف مستقل من نسخة خارج المضيف مع قياس RPO/RTO وقبول سريري/تشغيلي موثق. تمرين الاستعادة السابق كان إلى قاعدة منفصلة داخل المضيف نفسه.

المخاطر المتبقية عالية في السلامة السريرية والتعافي من فقد المضيف؛ سعة الموقع غير محسومة. الحزمة الثابتة مرشح اختبار، وليست النسخة النهائية المعتمدة للإنتاج.
