# إصلاح تعدد الفروع والتحقق — VIARA

تاريخ التقرير: 14 أكتوبر 2026. النطاق: إصلاحات المراجعة المتعمقة، مصدر الخادم والواجهة، الترحيلات، إعدادات حزمة النشر وصورة الخادم. جميع اختبارات PostgreSQL المذكورة استخدمت قواعد مؤقتة مستقلة وبيانات اصطناعية. لم تُستعد نسخة فوق قاعدة العميل، ولم تُستبدل مفاتيح التشفير الحالية.

## الملخص التنفيذي

أُصلحت المشكلات المؤكدة المتعلقة باختيار الفرع، العضوية، اختلاف المؤسسة، الأدوار، المطالبات والفواتير والمواعيد والتقارير، سياق قاعدة البيانات، البوابات، الوصول الحرج وحصص الترخيص. أُعيد فصل حساب تشغيل التطبيق عن مالك قاعدة البيانات، وأُنشئ حساب قراءة مستقل للنسخ الاحتياطي. نجحت مجموعتا الاختبارات، وترحيلات قاعدة جديدة وإعادة تطبيقها، وبناء الواجهة وصورة الخادم.

هذه نتيجة تحقق للمصدر والصورة المحلية، وليست إثبات نشر النسخة الجديدة على البيئة المشتركة أو اكتمال قبول المستخدمين واختبارات الحمل والتعافي في موقع العميل. أرشيف Offline القديم لا يتضمن هذه الإصلاحات؛ يجب إنتاج حزمة جديدة قبل تسليم الإصدار.

## الإصلاحات والتحليل

| المجال | المشكلة المؤكدة | الإصلاح |
|---|---|---|
| سياق الطلب | استخدام فرع من الاستعلام أو جسم الطلب مختلف عن الفرع الموثوق | مقارنة الفرع المطلوب بالسياق المعتمد ورفض التعارض؛ اشتراط فرع محدد للعمليات التي تعدل سجلاً |
| المطالبات والتأمين | تعديل مطالبة خارج الفرع، وتجاوز فرع التقارير من query | تقييد القراءة والتعديل بالفرع المختار وتمريره إلى خدمات التقارير |
| العضوية | عضوية بين مؤسستين، بيانات عضوية قديمة، دور فارغ يتراجع إلى Admin | تحقق المؤسسة في معاملة، إزالة ذاكرة العضويات المؤقتة، تثبيت الأدوار القديمة صراحة ورفض الدور غير المحدد |
| صلاحيات الموظف | تطبيق الدور العام بدلاً من دور الفرع في بعض المسارات | حساب الدور الفعلي مركزياً وإبقاء دور الهوية مستقلاً لإصدار الجلسات؛ منع منح Developer عبر عضوية فرع |
| إدارة الحسابات | إنشاء موظف دون مؤسسة أو عضوية، وإدارة حساب عالمي من مدير فرع | ربط المؤسسة والتحقق من مدير المؤسسة، إضافة العضوية عند اختيار فرع داخل معاملة، ومنع تعديل حساب مؤسسة أخرى أو حساب الخدمة |
| واجهة المستخدم | صلاحيات وبيانات الفرع السابق تبقى بعد التبديل | إلغاء الطلبات القديمة ومسح RTK cache والصلاحيات؛ إعادة تحميل صلاحيات الفرع وتجاهل استجابات فرع سابق |
| تسجيل الدخول | اختيار فرع غير مصرح أو أول فرع ضمناً | الاحتفاظ بالفرع فقط إذا كان ضمن العضويات الحالية؛ طلب اختيار عند تعدد الفروع دون افتراضي |
| عزل PostgreSQL | تشغيل التطبيق بمالك الجداول أو دور يتجاوز RLS | حساب rcms_app_user محدود، وفحص عند بدء الخادم يمنع SUPERUSER وBYPASSRLS وملكية الجداول المحمية |
| إثبات السياق | إمكانية تغيير GUC للفرع أو هوية المستخدم | توقيع HMAC قصير الصلاحية يشمل الفرع والهوية ونوع الفاعل؛ المفتاح في جدول خاص غير متاح للتطبيق |
| المعاملات والخلفية | SET LOCAL خارج معاملة أو غياب السياق للمهام المجدولة | سياق AsyncLocalStorage مستقل لكل طلب، إعداد تلقائي عند BEGIN، ومعرف خدمة مستقل لكل مؤسسة غير قابل لتسجيل دخول بشري |
| بوابة الطبيب | السياسة تعتمد على إحالة الفحص فقط وتفشل لموعد لم يبدأ فحصه | إسقاطات إحالة خاصة تُحدّث عبر triggers؛ دعم إحالة الموعد وإحالة الفحص دون إعادة دخول سياسات RLS recursively |
| بوابة المريض | سياق العاملين لا يناسب هوية المريض | سياسات قراءة للسجلات المملوكة للمريض النشط؛ إزالة سياسات الكتابة المباشرة غير المطلوبة للمواعيد |
| PACS/OIDC | غياب المؤسسة والتحقق الحديث من العضوية | قراءة المؤسسة وحالة حساب الخدمة من قاعدة البيانات ثم التحقق من الفرع؛ سياق خدمة فقط بعد التحقق من سر webhook |
| شاشات الانتظار | القراءة العامة تتوقف عند تفعيل RLS أو تقبل فرع مؤسسة أخرى | سياق خدمة محدد للفرع بعد التحقق من المؤسسة والفرع النشط، مع الإبقاء على إسقاط العرض وضوابط السرية |
| الوصول الحرج | تحقق المؤسسة permissive، واختلاف سلوك RLS عن السماح في middleware | تطابق المؤسسة، سياق موقّع مربوط بمنحة وجلسة، سياسات SELECT فقط للمواعيد والفحوص، تحقق الانتهاء والإلغاء ونطاق المورد |
| الترخيص | تجاوز انتهاء الترخيص، أو احتساب الحصة داخل الفرع فقط | قيود الحصص في التحقق قبل grace، منع الكتابة عند انتهاء الترخيص، وتجميع الاستخدام على مستوى النسخة بما يشمل جميع الفروع |
| النسخ الاحتياطي | حساب التطبيق المحدود لا يستطيع تصدير كل الصفوف | viara_backup_reader للقراءة فقط مع BYPASSRLS، اتصال BACKUP_DATABASE_URL مستقل، واتصال استعادة مستقل؛ مدير المؤسسة فقط للنسخة أحادية المؤسسة وDeveloper عند تعدد المؤسسات |
| إعداد العميل | متغيرات حسابات قاعدة البيانات الجديدة غير موجودة في إعداد قديم | تهيئة APP_DB_PASSWORD وBACKUP_DB_PASSWORD المفقودة فقط، دون تدوير أي مفتاح قائم، واختبار قابلية إعادة التشغيل |

الترحيلات الجديدة 207–212 متزامنة بين المصدر وحزمة النشر. لا يجوز تعديل ترحيل سبق تطبيقه في قاعدة فعلية؛ عند اكتشاف نسخة مطبقة تختلف بصمتها يجب استخدام ترحيل تصحيحي جديد بدلاً من تجاوز فحص checksum.

## المخاطر والحدود المتبقية قبل النشر

1. **عالٍ — البيئة المشتركة والحزمة القديمة:** لم تُنشر هذه الصورة تلقائياً في البيئة التي تعمل عليها جلسة أخرى. فحص سابق كشف إعدادات تشفير وتوقيع غير صالحة في تشغيل محلي؛ يجب معالجة إعداد البيئة مع الحفاظ على المفاتيح الأصلية لأي بيانات مشفرة. لا تكفي نتيجة بناء الصورة لإعلان تشغيل البيئة سليماً.
2. **عالٍ — الاستعادة:** نجاح سياسات حساب النسخ الاحتياطي لا يمثل دورة pg_dump/استعادة كاملة لكل المرفقات وPACS مع الإصدار الجديد. يلزم اختبار أرشيف مشفر كامل في بيئة مستقلة، وقياس زمن الاستعادة، وإعادة مزامنة مفتاح سياق الفروع عبر تشغيل migrate بعد الاستعادة قبل إعادة الخدمة.
3. **متوسط — الأداء:** لم يحدد العميل تزامناً متوقعاً ولم يوفر staging. تحتاج معاملات السياق وفحوص RLS إلى اختبار حمل ببيانات تمثل أحجام المواعيد والفحوص والدراسات، وقياس p95 واستهلاك الاتصالات. لا توجد نتيجة تحميل تبرر ضمان حد معين للمستخدمين أو حجم DICOM.
4. **متوسط — القبول التشغيلي:** يلزم تنفيذ سيناريو واقعي بفرعين: حجز، استقبال، دفع، فحص، تقرير، تسليم، تبديل الفرع، وقراءة المريض والطبيب؛ مع حساب يختلف دوره بين الفرعين، وسحب العضوية أثناء جلسة مفتوحة.
5. **حد معماري:** حصص الترخيص في هذا التنفيذ تخص النسخة المنشورة ككل. استضافة مؤسسات مستقلة تجارياً داخل قاعدة واحدة تحتاج نموذج تراخيص وملكية بيانات منفصلاً؛ وجود organization_id في الحماية لا يعني أن كل وحدات النظام أصبحت منصة SaaS متعددة المؤسسات.

هذه البنود بوابات تحقق ونشر، وليست نتائج اختبارات تم تنفيذها. لا تُغلق مهام قبول المستخدمين أو RPO/RTO أو الحمل في قائمة TODO اعتماداً على اختبارات الوحدات.

## خطوات إصدار النسخة الجديدة

1. حفظ نسخة كاملة قابلة للتحقق، وحفظ مفاتيح التشفير والتوقيع خارج أرشيف التوزيع العام.
2. تشغيل initialize-env.ps1 في مجلد الحزمة لإضافة كلمات مرور حسابات قاعدة البيانات المفقودة. لا تتغير المفاتيح الموجودة.
3. إنتاج أرشيف جديد بصور الخادم والواجهة الجديدة وتثبيت الصور بالبصمة؛ لا تُعدَّل حزمة Offline القديمة على أنها الإصدار الجديد.
4. تشغيل migrate بحساب مالك المخطط، ثم تشغيل backend باستخدام rcms_app_user فقط. كلمة مرور قارئ النسخ الاحتياطي مختلفة، والاستعادة تستخدم اتصالاً إدارياً محجوزاً لإجراء التعافي المعتمد.
5. تنفيذ اختبارات الدخان والقبول والاستعادة والحمل المذكورة، وتسجيل النتائج وحدود الأداء، ثم اعتماد النشر في نافذة صيانة مع خطة رجوع.
