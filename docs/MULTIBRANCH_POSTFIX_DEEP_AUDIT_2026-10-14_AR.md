# VIARA — مراجعة متعمقة لتعدد الفروع بعد الإصلاحات

**التاريخ:** 14 أكتوبر 2026. **قرار الجاهزية:** لا يُعتمد النشر النهائي قبل إغلاق النتائج الحرجة والعالية أدناه.

## الملخص التنفيذي

أعدت مراجعة المصدر بعد الإصلاحات، وشغّلت اختبارات الخادم والواجهة، ثم اختبرت حالات إضافية على PostgreSQL 15 بقاعدة جديدة تحتوي المخطط الحقيقي وجميع الترحيلات الـ212، وبحساب تطبيق فعلي محدود الصلاحيات. استُخدمت بيانات اصطناعية فقط، ولم تُنفذ استعادة فوق قاعدة العميل أو تغييرات في مفاتيحه.

نجحت الاختبارات الحالية: **1370 اختباراً للخادم ضمن 171 مجموعة، و784 اختباراً للواجهة ضمن 133 ملفاً**. رغم ذلك، أثبتت المراجعة **13 نتيجة مفتوحة: واحدة P0، وتسع P1، وثلاث P2**. تتضمن النتائج حالة البيئة المحلية القائمة، وهي متابعة تشغيلية وليست عيباً جديداً في المصدر.

أشد نتيجة هي فقدان حماية جداول الأمن الخاصة بعد الاستعادة. استطاع حساب التطبيق قراءة مفتاح توقيع سياق الفروع بعد استعادة dump وتشغيل migrate، ثم استخدامه لانتحال سياق مدير المؤسسة وقراءة **6001 موعد** عبر الفرعين. في القاعدة الجديدة قبل الاستعادة، كانت قراءة المفتاح مرفوضة كما ينبغي. هذا يحدد المشكلة في مسار التعافي وإعادة الأذونات، ولا يعني أن المفتاح مكشوف في التثبيت الجديد.

توجد أيضاً فجوات مؤكدة في الدور عند غياب اختيار الفرع، وإدارة RBAC، والإشعارات الحية، وإسناد المهام السريرية، ونقل الفحوص، والوصول الحرج وحصة المرضى. لذلك لا يصح اعتبار نجاح اختبارات الوحدات وحده إثباتاً لجاهزية الإصدار.

## المنهجية والأدلة

- تطبيق المخطط وجميع الترحيلات في حاوية PostgreSQL مؤقتة، مع كلمات مرور عشوائية واتصال محلي مستقل عن بيانات العميل.
- اختبار الدور الحقيقي `rcms_app_user`، وليس تنفيذ استعلامات النظام بحساب مالك الجداول.
- مقارنة الأذونات قبل الاستعادة، وبعدها، وبعد إعادة تشغيل migrate؛ ثم اختبار أثر التغير عملياً.
- اختبار حساب له دوران مختلفان بين الفرعين، وحساب يختلف دوره العام عن دوره السريري في الفرع.
- اختبار مُصدِر JWT الخاص بالوصول الحرج، وحواجز الدور الفعلية، وخدمات الإسناد وRBAC من المصدر.
- اختبار SSE بخادمه المنطقي الفعلي وبيانات مصطنعة، وحالة Redux والتخزين المشترك بين تبويبين.
- قياس عدّ المواعيد على 6001 سجل وقراءة خطة `EXPLAIN ANALYZE`؛ هذه قياسات محلية وليست اختبار حمل أو p95.
- فحص حالة الحاويات الحالية وخصائص إعداداتها دون تسجيل كلمات مرور أو مفاتيح.

الأدلة المنظمة موجودة في [مجلد الأدلة](audit-evidence/multibranch-deep-2026-10-14/). يتضمن `source-manifest.json` بصمات 27 ملفاً محل المراجعة. سجل المتابعة القابل للفرز: [قائمة النتائج CSV](MULTIBRANCH_POSTFIX_FINDINGS_2026-10-14_AR.csv).

## النتائج المؤكدة وأفضل مسار لإصلاحها

### R2-01 / P0 — الاستعادة تكشف مفتاح توقيع السياق وتتيح تعديل إسقاطات صلاحيات البوابة

**الدليل:** كانت امتيازات حساب التطبيق قبل الاستعادة `context_secret_read=false` و`portal_acl_write=false`. بعد `pg_dump` و`pg_restore` بنفس خيارات الخدمة، أصبحت الاثنتان `true`. بقيتا كذلك بعد migrate. نجح تكوين توقيع باستخدام المفتاح المقروء من قاعدة البيانات والدخول بسياق مدير المؤسسة، فظهر 6001 موعد بدلاً من نطاق الفرع.

**السبب:** تستخدم خدمة النسخ والاستعادة `--no-privileges`. لا تُستعاد قيود REVOKE الخاصة، بينما تمنح الأذونات الافتراضية في الترحيل 206 امتيازات لحساب التطبيق على الجداول المعاد إنشاؤها. إعادة migrate تتجاوز الترحيلات المسجلة ولا تعيد تطبيق REVOKE للجداول الخاصة. مزامنة قيمة المفتاح وحدها لا تصلح أذوناته.

**الأثر:** فقدان دفاع قاعدة البيانات ضد تزوير السياق بعد التعافي. يتطلب الاستغلال وصولاً لتنفيذ SQL بحساب التطبيق، مثل ثغرة SQL injection أو انكشاف بيانات الاتصال؛ لم أثبت وجود نقطة HTTP تسمح بتنفيذ SQL اعتباطي. لكن الاختبار أثبت أن الحماية المصممة لهذا التهديد تصبح قابلة للتجاوز.

**الإصلاح:** إجراء موثوق وقابل لإعادة التنفيذ لإصلاح GRANT/REVOKE بعد كل استعادة، وإلزام أداة الاستعادة بتنفيذه والتحقق منه قبل إعادة الخدمة. يشمل جداول المفتاح والإحالات الخاصة وأذونات وظائف SECURITY DEFINER. لا يُكتفى بترحيل يُنفذ مرة واحدة أو بفحص NOBYPASSRLS. تبقى مفاتيح الإصدار الخاصة خارج التوزيع، ولا تُطبع مفاتيح السياق أثناء التحقق.

**اختبار الإغلاق:** استعادة كاملة ثم migrate؛ رفض SELECT للمفتاح وUPDATE لإسقاطات البوابة؛ فشل السياق المزور، مع استمرار عمل القراءة المصرح بها للمريض والطبيب والموظف.

**المراجع:** `backend/src/services/postgresBackupService.js:229,437`، `database/migrations/206_multibranch_row_level_security.sql:28`، `database/migrate.js:378`. الدليل: `database.json` → `beforeRestore`, `afterRestoreAndMigrate`, `afterRestoreForgedContext`.

### R2-02 / P1 — غياب الفرع يعيد الدور العام ويمنح Admin رغم اختلاف أدوار العضويات

حساب دوره العام Admin وعضوياته Receptionist وNurse دون فرع افتراضي أُجيز له طلب بسياق `branchId=null`، ثم أصبح دوره الفعلي Admin، وقَبِله حاجز Admin. المسار الاختياري في middleware يسمح بالسياق الفارغ، و`effectiveRole` يتراجع إلى دور الحساب.

**الإصلاح:** فصل صلاحيات الهوية العامة عن صلاحيات العمل في الفرع. الموظف العادي الذي يحتاج اختياراً يجب أن يحصل على `BRANCH_SELECTION_REQUIRED` أو دور غير مخوّل للعمل، دون الرجوع للدور العام. تبقى مسارات استعادة الهوية المحددة متاحة حسب تصميمها.

**اختبار الإغلاق:** حذف `x-branch-id` من حساب متعدد الفروع لا يفتح مسار Admin أو مساراً محمياً بدور فرع. المراجع: `branchContextMiddleware.js:291`، `effectiveRole.js:7`. الدليل: `database.json` → `optionalBranchRole`.

### R2-03 / P1 — مدير فرع يستطيع تعديل صلاحيات دور على مستوى النظام كله

حساب ليس مدير مؤسسة، ودوره العام Receptionist ودور الفرع Admin، اجتاز `MANAGE_ROLES` واستطاع حذف صلاحيات Nurse العامة؛ انتهى الاختبار باستجابة 200 وعدد صلاحيات Nurse يساوي صفرًا. جدول `role_permissions` عام، وحاجز إدارة الأدوار لا يشترط صلاحية إدارة المؤسسة.

**الإصلاح:** حصر تعديل السياسة العامة بمدير المؤسسة أو المسؤول التقني وفق سياسة واضحة. إذا كانت سياسات الفرع مطلوبة، تُحفظ منفصلة بمفتاح الفرع، دون تعديل السياسة العامة المشتركة.

**اختبار الإغلاق:** مدير الفرع يحصل على 403 عند تعديل السياسة العامة، وتبقى صلاحيات الفرع الآخر سليمة. المرجع: `backend/src/controllers/rbacController.js:102` ومسارات RBAC. الدليل: `database.json` → `branchAdminGlobalRbac`.

### R2-04 / P1 — سياق الفرع لا يصل إلى تخزين الإشعارات وتوزيع SSE

ثبتت ثلاث حالات مترابطة: إرسال إشعار مع `branchId=B` حفظ `notifications.branch_id=NULL`؛ توزيع إشعار فرع B إلى دور Admin أوصله لاتصال فرع A؛ وهوية الاتصال التي يتلقاها فلتر قنوات المحادثات تحتوي `userId,role` فقط، فتغيب `branchIds` ويُرفض بث قناة الفرع حتى للعضو الصحيح.

**الإصلاح:** تمرير الفرع والمؤسسة حتى الحفظ والتوزيع، وتحديد جمهور الحدث بعضوية ودور صالحين في الفرع. الاشتراك الحي يحتاج تحققاً عند الاتصال وعند تغير العضوية أو الجلسة، مع إعادة ربطه عند التبديل. يفضّل إرسال إشعار محدود لتحديث البيانات، ثم تحميل التفاصيل عبر API يعيد التحقق من الصلاحية.

**اختبار الإغلاق:** لا يصل محتوى إشعار B إلى موظف A غير المصرح له، وتصل قناة A لعضوها الصحيح؛ سحب العضوية يوقف التسليم. المراجع: `notificationService.js:85,437`، `realtimeService.js:128,153,348`. الأدلة: `database.json` → `notificationBranchPersistence` و`realtime.json`.

### R2-05 / P1 — حصة المرضى تعتمد على عمود غير موجود في المخطط الحقيقي

استدعاء `license_quota_usage('patients')` على القاعدة الجديدة أعاد `42703: column "is_active" does not exist`. المخطط يستخدم `patient_status`. عند تفعيل حصة النسخة التجريبية، يتعذر التحقق وتُحجب العملية بخطأ خدمة؛ اختبار قاعدة مصغرة يضيف عموداً اصطناعياً لا يكشف المشكلة.

**الإصلاح:** احتساب المرضى باستخدام الحالة الموجودة فعلياً وتعريف الحصة المتفق عليه. يُنفذ التصحيح بترحيل جديد إذا طُبق 212، دون تعديل بصمته القديمة.

**اختبار الإغلاق:** إنشاء مريض تحت الحد ورفضه عند الحد على المخطط الحقيقي، دون إضافة أعمدة في fixture غير موجودة في الترحيلات. المرجع: `database/migrations/212_license_quota_aggregate.sql:7`. الدليل: `database.json` → `patientQuota`.

### R2-06 / P1 — نقل الفحص يفشل تحت سياق فرع محدد رغم عضوية المصدر والهدف

تغيير `examinations.branch_id` من A إلى B أعاد 42501 بسبب WITH CHECK، رغم وجود العضويتين. سياق A لا يسمح بكتابة صف في B. نجح التغيير في الاختبار عندما استُخدم سياق مدير المؤسسة لجميع الفروع، وهو اختلاف مهم عن تشغيل الواجهة في فرع مختار.

**الإصلاح:** عملية نقل ذرية محددة الصلاحية تتحقق من المصدر والهدف والمؤسسة والحالة والأجهزة، وتنقل الفحص والموعد وتكتب سجل التدقيق. يجب أن يكون إذن النقل ضيقاً، وليس تعطيل RLS أو تشغيل الخادم بمالك قاعدة البيانات.

**اختبار الإغلاق:** نجاح النقل من فرع مختار مع الصلاحيات المطلوبة؛ رفض المؤسسة الأخرى والهدف غير المصرح؛ المحافظة على الصورة والفرع الأصلي والأثر المالي. المرجع: `backend/src/controllers/examController.js:1870,1958`. الدليل: `database.json` → `branchTransfer`.

### R2-07 / P1 — إسناد المهام يعتمد على الدور العام للموظف المستهدف

موظف دوره في A هو Nurse لكن دوره العام Receptionist رُفض بـ `ROLE_NOT_ELIGIBLE`. في الاتجاه العكسي، موظف دوره العام Nurse ودوره في A هو Receptionist أُسندت إليه مهمة Nurse بنجاح. الاستعلام لا يجلب `organization_id` أيضاً، رغم تمريره لاحقاً لدالة العضويات.

**الإصلاح:** تحديد الفرع من المهمة أولاً، ثم جلب العضوية الفعالة والدور والمؤسسة للمستهدف داخل المعاملة. صلاحية مقدم الطلب لا تجعل الموظف المستهدف مؤهلاً؛ يجب فحص الاثنين بصورة مستقلة.

**اختبار الإغلاق:** قبول دور الفرع السريري الصحيح ورفض الدور غير السريري، بغض النظر عن الدور العام. المرجع: `clinicalTaskAssignmentService.js:251,253,268`. الدليل: `database.json` → `branchClinicalAssignment`.

### R2-08 / P1 — تعارض الدور يعطل الوصول الحرج وتوثيق رمزه

حاجز المسار رفض `EmergencyClinicalViewer` باستجابة 403 لأن الدور غير ضمن قائمة الأدوار السريرية. في حالة أخرى صحيحة العضوية، حساب عام Technician يعمل بدور Radiologist في الفرع حصل على رمز وصول حرج بدور Radiologist؛ رفضته المصادقة التالية بـ401 لأن دور الهوية في قاعدة البيانات Technician.

**الإصلاح:** إصدار JWT بدور الهوية الثابت، وحساب دور الفرع بصورة مستقلة عند الطلب. السماح بالقراءة الحرجية عبر capability مرتبطة بمنحة وجلسة ومورد، مع استمرار رفض الكتابة. لا يُعالج التعارض بإزالة تحقق دور الحساب من المصادقة.

**اختبار الإغلاق:** دخول وقراءة حرجية ناجحة عند اختلاف الدور العام عن دور الفرع، ثم منع الوصول فور الإلغاء والانتهاء، ورفض الكتابة والمؤسسة الأخرى. المراجع: `rbacController.js:57,206`، `authMiddleware.js:189`. الأدلة: `database.json` → `emergencyRoleRoute`, `emergencyTokenIdentity`.

### R2-09 / P2 — تكلفة سياسات RLS مرتفعة في استعلام تجميعي بسيط

على 6001 موعد، عدّ الصفوف بحساب التطبيق استغرق **1.24–1.40 ثانية** في العينات النهائية المحفوظة، مقابل بضعة ميلي ثانية للقراءة بحساب المالك دون سياسات. أظهرت الخطة Seq Scan مع وظائف السياق والفرع والبوابات والوصول الحرج، وأكثر من 33 ألف إصابة buffer. حساب التطبيق رأى 3001 صفاً، والمالك رأى 6001؛ المقارنة تبين تكلفة الحماية، ولا تمثل طلبين بصلاحيات متطابقة أو قياس p95.

**الإصلاح:** تقييم إثبات التوقيع والسياق مرة لكل statement، وتجهيز نطاق الفروع المصرح به مرة، وصياغة predicates قابلة للاستفادة من الفهرس. تُراجع تكلفة سياسات البوابة والطوارئ على استعلامات الموظفين دون إضعاف العزل.

**اختبار الإغلاق:** مقارنة خطط وقياسات على نفس البيانات قبل التحسين وبعده، ثم حمل متزامن بمقاييس p95 والاتصالات. الدليل: `database.json` → `performance`.

### R2-10 / P2 — تبويبان قد يرسلان طلبات بفرعين مختلفين داخل مساحة عمل واحدة

بقي Redux في الفرع A، لكن بعد تغيير localStorage بواسطة تبويب آخر، أعاد `getActiveBranchId()` الفرع B. `configureActiveBranchProvider` موجود دون توصيله بالمتجر، بينما طلبات RTK تستخدم حالة Redux عند وجودها. تظهر بذلك مصادر مختلفة لفرع الطلب.

**الإصلاح:** مصدر واحد للفرع لكل مساحة عمل، واختيار سياسة صريحة لعزل التبويبات أو مزامنتها. لا يُستخدم التخزين المشترك بديلاً عن اختيار محلي فارغ بصورة ضمنية.

**اختبار الإغلاق:** كل أنواع الطلبات تعرض وترسل نفس فرع مساحة العمل بعد تبديل تبويب آخر. المرجع: `frontend/src/utils/branchContext.js:10,14`، `store/baseApi.js`. الدليل: `frontend.json` → `crossTab`.

### R2-11 / P2 — إعادة الجلسة لا تعيد التحقق من الفرع المخزن

بعد وصول بيانات عضوية جديدة تسمح بالفرع A فقط، احتفظ `rehydrateUser` بالفرع B القديم، وأصبح الدور Unassigned. التحقق الموجود في `setCredentials` لا يُطبق في مسار إعادة الجلسة؛ يؤدي ذلك إلى طلبات 403 ومساحة عمل عالقة رغم وجود عضوية صالحة.

**الإصلاح:** توحيد تطبيع المستخدم والمؤسسة واختيار الفرع بين الدخول وإعادة الجلسة وتحديث الحساب، مع إبطال البيانات والطلبات القديمة إذا تغير النطاق.

**اختبار الإغلاق:** سحب عضوية B ثم refresh يعيد فرعاً صالحاً أو شاشة اختيار واضحة. المرجع: `frontend/src/store/authSlice.js:184`. الدليل: `frontend.json` → `rehydrate`.

### R2-12 / P1 — بعض المسارات تستبدل مؤسسة المستخدم بالمؤسسة الافتراضية

لعضوية صحيحة في مؤسسة ذات UUID غير افتراضي، أعادت `getUserBranches(db,user,false)` صفر فروع، بينما أعاد الاستدعاء نفسه مع UUID المؤسسة فرعاً واحداً. توجد استدعاءات ناقصة في المحادثات والإشعارات والتحويل وHR. هذه مشكلة حتى عند نشر نسخة لمؤسسة واحدة ذات UUID مختلف، وليست مقتصرة على SaaS متعدد المؤسسات.

**الإصلاح:** جعل معرف المؤسسة مطلوباً في الاستدعاءات الخاصة بالموظفين، ومراجعة جميع callers، وإضافة `organization_id` لاستعلام المستهدف في الإسناد السريري. لا يُستبدل غياب السياق الموثوق بافتراضي صامت.

**اختبار الإغلاق:** نجاح نفس السيناريو بمؤسسة UUID غير افتراضي، ورفض عضوية مؤسسة أخرى. أمثلة: `chatController.js:84`، `notificationController.js:106`، `examController.js:1914`، `hrController.js:852,961`. الدليل: `database.json` → `nonDefaultOrganization`.

### R2-13 / P1 — حاويات Docker المحلية القائمة لا تعمل بالإصدار المراجع

أظهر الفحص `VIARA_backend` في حالة restarting على صورة قديمة تختلف عن صورة المراجعة، وباتصال لا يستخدم `rcms_app_user`. البيئة تعمل بوضع development، وخصائص مفاتيح التشفير والتوقيع لا تطابق متطلبات الإنتاج. أظهر OHIF حالة unhealthy. هذه لقطة تشغيلية؛ لا تحدد وحدها السبب النهائي لفشل كل خدمة.

**الإصلاح:** إعداد نافذة تحديث بعد إغلاق نتائج المصدر، والتحقق من الصورة والأذونات والإعدادات وhealth checks. تُستعاد المفاتيح الأصلية لأي بيانات مشفرة؛ لا تُستبدل عشوائياً لتحسين حالة الفحص. صحة صورة محلية جديدة لا تثبت صحة الحاويات القائمة.

**اختبار الإغلاق:** API مستقر وOHIF/PACS صالحان للمسار المقصود، دور قاعدة البيانات صحيح، وصور مثبتة بالبصمة ومطابقة للحزمة المسلّمة. الدليل: `runtime.json`، دون قيم أسرار.

## أثر النتائج على قائمة المهام

لا تُغلق المهام اعتماداً على وجود ملف أو endpoint فقط. خصوصاً:

- نقل الفحص الموثق في MBT-503 وMBT-410 يحتاج إعادة قبول تحت حساب التطبيق وسياق الفرع المختار.
- مهام عزل قاعدة البيانات MBT-801/802/803 تحتاج اختبار استعادة، وليس تثبيتاً جديداً فقط.
- مهام الأدوار والوصول الحرج والإشعارات تحتاج سيناريو اختلاف أدوار الفرعين وسحب العضوية أثناء الجلسة.
- قياسات الأداء وRPO/RTO وقبول المستخدمين تبقى أعمال تحقق مستقلة؛ لم تُثبتها اختبارات الوحدات.

لم أغيّر حالات TODO تلقائياً؛ سجل CSV يحدد النتائج المفتوحة واختبار إغلاق كل منها.

## ترتيب المعالجة وبوابات الإصدار

1. إصلاح أذونات التعافي R2-01 أولاً، ثم إعادة تجربة dump/restore كاملة بحساب التطبيق والتوقيع المزور.
2. إغلاق حدود التفويض R2-02/03/04/07 قبل توسعة الاستخدام أو إتاحة البوابات عن بُعد.
3. إغلاق مسارات التشغيل R2-05/06/08/12، ثم قبول دورة كاملة في فرعين بمؤسسة UUID غير افتراضي.
4. معالجة اتساق الواجهة R2-10/11، وقياس أثر R2-09 تحت حمل يمثل حجم العميل.
5. إنتاج حزمة نشر جديدة، والتحقق من R2-13 ودورة الاستعادة والمرفقات وPACS، ثم اعتماد النشر. الحزمة القديمة لا تُعد إصداراً محدثاً بمجرد تعديل المصدر.

لا تحتاج هذه الخطة إلى تعديل ترحيلات مطبقة؛ تُستخدم ترحيلات تصحيحية جديدة، مع إجراءات أذونات قابلة لإعادة التنفيذ بعد التعافي. تُحافظ الاختبارات على حالات الرفض والحالات المسموح بها معاً.

## إعادة تنفيذ المراجعة

من جذر المستودع، مع تثبيت اعتماديات الخادم والواجهة وتشغيل Docker للاختبار الأول:

```powershell
node scripts/fixtures/audit-multibranch-deep-postfix.cjs
node scripts/fixtures/audit-multibranch-frontend-postfix.mjs
node scripts/fixtures/audit-multibranch-realtime-postfix.cjs
node scripts/fixtures/audit-multibranch-runtime-postfix.cjs
```

الأول يُنشئ ويحذف قاعدة مؤقتة ذات اسم مستقل؛ لا يستخدم DATABASE_URL الحالي للاتصال ببيانات العميل. فحص runtime قراءة فقط ويفترض أسماء الحاويات المحلية الواردة بالتقرير. كل probe يُخرج أدلة على السلوك الحالي؛ نجاح تشغيله يعني اكتمال الفحص، وليس زوال العيب. المخرجات تُكتب إلى scratch، والنسخة المنظمة المصاحبة للتقرير محفوظة في مجلد الأدلة.

## حدود الاستنتاج

هذه المراجعة أثبتت العيوب المذكورة ولم تثبت وجود SQL injection أو اختراق لبيانات العميل. لا تتضمن اختبار اختراق خارجي، أو تشغيل DICOM كبير عبر WAN، أو اختبار حمل شامل، أو استعادة مرفقات وصور فعلية. قياسات الأداء مرتبطة بالجهاز والبيانات المستخدمة. وجود جلسة تطوير أخرى يستلزم مقارنة بصمات المصدر عند تنفيذ المعالجة أو بناء الحزمة التالية.
